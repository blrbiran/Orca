### Important

1. **Incomplete capsule identity and normalization validation can assign a typed cause and evidence to the wrong execution.** `executionFormatFailureSchema` requires `identity.envelopeHash`, but `DiagnosticRun` has no corresponding field and the match omits it (`src/control/savedResultProtocol.ts:46-58`, `src/panel/runDiagnosis.ts:14-30`). A hash-valid capsule with all compared IDs but another envelope hash is accepted as this run. The normalization parser also accepts only `status` and `reason` with `.passthrough()`, so it admits a missing or contradictory `diagnostic` even though the paired normalizer’s typed unavailable result includes that diagnostic (`src/panel/runDiagnosis.ts:18-30`; `ccloop/src/runtime/executionNormalizer.ts:3-22`). Because the same helper supplies evidence refs (`src/panel/controlViews.ts:1065`), the weakness affects both cause and manifest membership. Bind the capsule to the run’s stored envelope hash and validate the full typed normalization result; add negative tests for wrong envelope and malformed/contradictory diagnostic. The existing test only changes `runId` (`tests/panel/runDiagnosis.test.ts:21-25`). This is required by design §5’s typed direct cause/authorized evidence rule.

2. **Failed runs without raw reason/code lose the required explicit unknown diagnosis.** `RunReason` returns the lineage before rendering diagnosis whenever raw reason and failure code are null and state is not exactly `blocked` (`web/src/RunReason.tsx:13-16`). `settled-failed` is a failed state, and `runReasonText` permits null for it (`web/src/runFacts.ts:11-29`); nullable reasons are allowed on the run view (`src/control/webProtocol.ts:1270-1278`). The same applies to a historical failed outcome with missing strings. Show phase/attempt/unknown cause for any failed run, including settled failure, and cover a null-reason fixture. Design §5 asks for an explicit unknown cause on failures (`docs/superpowers/specs/2026-10-11-feedback-followup-design.md:39`).

3. **The operator skill still gives a resend-first instruction for an uncertain timeout.** It says to resend the same command after any timeout or retryable error (`skills/orca-control/SKILL.md:119-123`), then says a missing genuine group must not trigger an automatic resend (`skills/orca-control/SKILL.md:124-127`). In the documented missing-group scenario the first instruction is the action the second is trying to prevent. Make retained-result lookup the first step for an uncertain outcome, and describe when a same-ID retry is safe after a confirmed ordinary miss. The shared design requires lookup first and no automatic resend (`docs/superpowers/specs/2026-10-11-feedback-followup-design.md:31-35`).

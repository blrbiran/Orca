## Important

1. **A crash during stale-lock reclamation can permanently block all future applies.** [`updateReceipt.ts:111-120`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updateReceipt.ts:111) acquires the reclaimer guard by `mkdir(root/reclaim)`, and only the current process removes it in `finally`. If that process dies after `mkdir` but before moving the stale `lock`, subsequent processes always get `EEXIST`, loop on the guard, and eventually report a lock timeout at [`updateReceipt.ts:123`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updateReceipt.ts:123). Neither the guard nor its owner is recovered. This violates the amendment's cross-process stale recovery, especially in the crash windows Task 9 is required to handle. Give the reclaim guard a durable owner/recovery rule or use an atomic stale-lock removal design without an orphanable secondary guard; add a crash test at this window. The current two-process recovery test kills the apply owner, not the reclaimer ([`updateRecovery.test.ts:82`](/private/tmp/ccloop-feedback-followup-task9-20261011/tests/agents/updateRecovery.test.ts:82)).

2. **Path and addition previews can use the wrong version for the exact command they offer.** Existing rows are correctly observed with the entire configured argv at [`updates.ts:83-87`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updates.ts:83). But discovery probes only `[candidate.path]` at [`detect.ts:83-85`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/detect.ts:83), while a path choice is published as `[candidate.path, ...row.command.slice(1)]` at [`updates.ts:104-107`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updates.ts:104) and re-probed with that full argv at [`updates.ts:129-134`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updates.ts:129). A CLI whose `--version` depends on preserved custom args can be omitted as unavailable or advertised with a version that apply then always rejects as stale. Addition choices have the analogous draft-args gap ([`detect.ts:94-103`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/detect.ts:94), [`updates.ts:109-116`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updates.ts:109)). Probe and bind each offered choice's exact argv during preview. The path test's injected probe returns one version regardless of argv, so it misses this case ([`updates.test.ts:65-74`](/private/tmp/ccloop-feedback-followup-task9-20261011/tests/agents/updates.test.ts:65)).

## Minor

1. **Completed replay still depends on a valid current table before opening its receipt.** [`updates.ts:136-147`](/private/tmp/ccloop-feedback-followup-task9-20261011/src/agents/updates.ts:136) reads/parses the table before the lock and completed-receipt check. If a completed operation is replayed after the table becomes unreadable or malformed, the immutable receipt cannot be returned, although no CAS is needed. The amendment specifically says to return the matching completed receipt before the base-hash check. Moving this pre-read inside the new-operation branch would make replay independent of current table health while keeping the existing identity checks.

## Critical

1. **An unsupported replacement peer can erase an unknown pending apply.** Startup reconciliation replays a pending request at `src/control/agentUpdates.ts:152-169`. If the configured binary is now an older peer, the feature gate throws `control-agent-update-unsupported` before reading the original operation (`src/control/ccloopPort.ts:123,130`). The catch at `src/control/agentUpdates.ts:170-172` then calls `finalizeKnownRefusal`, which books a terminal 422 and marks the outbox complete (`src/control/agentUpdates.ts:113-125`). A previous Task 9 invocation may already have renamed the table or written its receipt before Orca lost the answer. The later unsupported feature probe proves nothing about that prior mutation. This violates the §4 matching-receipt-only reconciliation rule and releases the one-pending-operator fence. Preserve an existing pending row as unknown when a later peer cannot produce its same-operation receipt; keep the fresh first-dispatch old-peer refusal terminal. Add an actual unknown-then-old-peer regression criterion.

## Important

1. **Recovered commands lose the original client and principal.** Reservation stores `principal` and `client` (`src/control/agentUpdates.ts:82-84`), and reconciliation reads them (`src/control/agentUpdates.ts:153`) but finalizes without restoring the command context (`src/control/agentUpdates.ts:169-174`). The ledger writes attribution only from `commandClientFor`/`commandPrincipalFor` (`src/control/commandLedger.ts:270-282`), so a post-restart success or stale refusal gets NULL attribution. Wrap reconciled finalization in the stored `withCommandContext` and assert the terminal row retains the original owner/client after a crash.
2. **The update writer bypasses the shutdown admission gate.** `WebControlService.applyAgentUpdate` reserves, awaits the peer, and finalizes without `admissionGate.enter()` (`src/control/webService.ts:698-716`). Shutdown waits for admitted work only (`src/control/admissionGate.ts:18-42`, `src/panel/controlLifecycle.ts:183-187`). Thus an apply can begin after drain or remain in flight while shutdown proceeds; unlike neighboring async writers, it is not fenced against store closure. Admit the whole reserve→peer→finalize operation, release in `finally`, and cover a held-peer/shutdown race.

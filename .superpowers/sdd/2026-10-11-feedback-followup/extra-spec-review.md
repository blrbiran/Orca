## F1 — Bind recovery to the current task's unchanged semantic authority [P1]

Evidence: saved-result spec lines 15, 21 and 27 bind the old capsule and require current run membership, but line 31 uses “current approved recovery selection and limits” without naming which current changes invalidate old work. Existing Orca continuation separately compares predecessor/current `graphVersion`, `targetVersion` and `configHash` (`src/control/continuation.ts:35-36`), and requires the latest selected predecessor (`:147`). Task retry reads current confirmed task authority (`src/control/retryTask.ts:112-114`). A source capsule can pass every old hash while the task was amended, the write set widened, dependencies changed, or a newer task run superseded it. Expected command revision alone does not prove semantic compatibility.

Correction to append: admission and the final pre-spawn check must require the source to be the current failed task attempt, with no newer task run or pending ordinary retry/recovery, and match current group/work/task, graphVersion, targetVersion, frozen task contract and acceptance/safety/write-set authority. Refuse `saved-result-source-stale` or a specific authority mismatch when they differ. Preserve the original base/attempt snapshot; never rebase or substitute the current target tree before verification. Current target tip movement alone may remain legal through ordinary reconciliation/landing conflict checks. Explicitly identify allowable recovery differences: fresh funded allowance, runtime limits and approved verifier selection/provenance; none changes the task goal, saved code, original plan or source identity. Tests must cover a revision-current request selecting semantically stale evidence, a later failed attempt, pending retry, and target-tip drift that safely reaches ordinary reconciliation.

## F2 — Verification must not repair or replace the saved candidate [P1]

Evidence: saved-result spec lines 29-31 validate the restored snapshot before invoking real checks/verifier, then use ordinary write-set checks. Those checks establish path authority, not that the verified candidate is still the saved one. Claude's verifier prohibition is a prompt (`ccloop src/runtime/claude/prompts.ts:76`); the runner enables normal tools for phases other than single-call (`scripts/claude-phase-runner.mjs:510-521`). Codex uses a read-only phase sandbox (`src/runtime/codex/runCodexPhase.ts:29`), but controller-run validation commands may still write files. Therefore “skip execute” alone permits a verifier or check to repair code within allowed paths and land it as recovered saved output.

Correction to append: record the controller-measured candidate tree/index and protected untracked input identity after restoration and before validation. Compare it after checks/verifier, before Results verification publication and harvest. Any change to saved candidate files, modes, deletions or index fails recovery with a typed `saved-result-modified-during-verification`; no retry loop, executor call or landing. Validation scratch/output may be permitted only through explicit declared output paths or controller-owned locations outside the candidate, and excluded from harvest. Persist recovery mode and allowed phase set through accepted envelope, run state and crash/adoption paths; all resume paths remain incapable of planner/executor entry. Add tests where a command and a Claude-style verifier mutate an allowed source file, and a crash/adoption path would otherwise enter the normal loop. Existing normal verification behavior need not be changed globally.

## F3 — Installation apply needs one serialization fence around CAS and publication [P1]

Evidence: agent spec line 19 says CAS current hash, re-probe, validate, atomic rename; line 21 exposes helpers through both structured control and CLI. Atomic rename prevents truncation but does not prevent two processes from both reading the same base hash, asynchronously probing, then overwriting each other's accepted changes. Existing probes are asynchronous subprocess calls (`ccloop src/agents/materialize.ts:23-46`), and current table reads provide a private no-follow handle but no writer lock (`src/agents/table.ts:67-87`). A panel-only admission gate would not serialize a direct CLI apply.

Correction to append: all shared apply entry points take the same exclusive table-update lock; under that lock read the private current table, check the exact base hash, verify owned immutable preview/change identities, re-probe and compare the accepted exact argv/realpath/version observation, validate, recheck current bytes immediately before publication, and atomically replace. No first-check-then-unlocked-probe sequence. Refuse stale/conflict after an intervening update. Record a durable apply receipt keyed command identity and preview/accepted-change hash, so crash after rename but before Orca command receipt cannot misclassify the already-applied command as an unexplained stale failure or repeat it. Add a two-process apply race and crash-after-rename test. Preserve modes/private parent checks. Probe timeout/overflow must also settle the probe process tree before returning; current `child.kill` plus immediate `finish` is insufficient for configured wrappers that spawn children (`materialize.ts:34-43`).

## F4 — Name the allocation slot domain and renewal count equation [P2]

Evidence: token spec line 17 divides by “configured concurrency minus active claims”, but global/project caps span several groups while scheduler dispatch is scoped by group. Existing cap commitments sum active runs across the cap scope (`Orca src/control/spendCaps.ts:26-36`), and claim checks are group-based (`:70-85`). Different denominator domains produce different actual grants; handoff reservation and very small headroom also affect whether more than one unlimited task can start. Line 19 requires carried counts but does not say whether protocol counts are run-local or lineage cumulative. ccloop emits run-local `attempts: observation.attempt, sessions: 1` (`src/control/worker.ts:245-264`); Orca existing continuation derives remaining allowance from predecessor consumption (`src/control/continuation.ts:38-43`).

Correction to append: choose and state one authoritative slot domain, e.g. the owning dispatcher/group's configured concurrency and currently admitted worker leases, while cap headroom/commitments always include every in-scope claim from every group. Count accepted/start-unknown leases as occupied, exclude terminal released leases, and do not count verifier/estimator/reconcile slots as ordinary worker slots unless the selected concurrency policy actually includes them. State a precise prospective-handoff and positive useful-work rule, including headroom insufficient to fund all otherwise free slots; avoid parking forever only because an idle-slot denominator rounds work to zero. For renewal, persist finite inherited consumption separately from fresh run-local observations, grant non-token remainder as authored limit minus all lineage usage, and add each new run's actual usage exactly once. One renewed session and newly entered attempt must consume one remaining unit; replay consumes none. Test cross-group cap claims, tiny headroom/handoff, start-unknown occupancy, count exhaustion at renewal and cumulative usage not double-booked. Soft overshoot remains measured spend/deficit and prevents further admission; no guarantee should be invented.

## F5 — Specify primary inheritance for partial role overrides and freeze hash compatibility [P2]

Evidence: agent spec line 7 inherits group primary only with “no explicit role override”, while priority and same-agent rules are preserved. Current role storage allows field-only selections; current estimator baseline is operator default, then operator role, then group role (`Orca src/control/agentSelection.ts:74-78`), and each field is associated with the effective agent of its layer (`:91-114`). With operator primary A, saved `{model: A-model}` estimator override, and group primary B, inserting group-primary underneath the old role layer can carry A-model onto B; inserting it above can discard an explicit role choice. Line 11 also requests a selection/provenance hash, whereas current `selectionsHash` hashes only partial/selection/configHash (`:135-142`).

Correction to append: define partial override semantics explicitly. Recommended compatible fence: absent/empty role layers inherit full resolved group primary; an operator role with any concrete field retains its existing operator-agent association, resolving against operator primary/perAgent first; group role fields overlay that resolved role baseline, and an explicit role-agent switch discards other-agent model/context exactly as today. A null panel field retains current mask/inherit semantics. Never reinterpret historical field-only role values as another installation's model/context merely because group primary changed. Provide examples for empty/null, operator model-only, group model-only and explicit agent overrides. Name source provenance per field, keep old frozen records/hashes unchanged, and version any new provenance-inclusive freeze hash/domain rather than changing verification of old records. Confirm uses authoritative server resolution, and required estimate failures remain local; no-estimate import remains usable.

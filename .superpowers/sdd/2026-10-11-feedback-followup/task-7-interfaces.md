# Task 7 concrete consumer interfaces

The implementation is based on Task 6 producer commit `299da37f5b9781f79f530b871b37218a3cef7bec`, and the binding saved-result design through §§6.13–6.14. Core protocol 3 collections remain unchanged. Private recovery channels have independent strict Zod mirrors in `src/control/savedResultProtocol.ts` and are available only through the explicitly paired feature-capable ccloop binary.

## Read and command surfaces

- `GET /api/control/runs/:runId/saved-result-eligibility`, existing authenticated control-read boundary. The controller returns strict `{status:'unavailable',reason}` or the Task 6 source eligibility DTO: `{status:'eligible',authorityKind,sourceIdentity,rawExecutionTokens,recoveryOf,limitation}`. It checks current membership, exact source identity, graph/target/frozen contract, failed source, booked accounting and valid old-owner stop/settlement receipts. It creates only a disposable private source package, no run/command/claim/reservation/provider authorization. Source state is re-read after the async private probe. Unsupported default old peer is visible as `control-saved-result-unsupported`.
- `POST /api/control/groups/:groupId/tasks/:taskId/verify-saved-result` uses the existing authenticated mutation route and ledger client/principal checks. The raw verb is task-scoped, with strict payload `{sourceRunId,sourceAttempt,capsuleHash}` and the current `expectedRevision`; no extra payload keys. Member/agent permission follows ordinary retry's existing authority. Successful ledger result is `{kind:'saved-result-verification-started',taskId,runId,recoveryOf}`. Replay returns the same fresh run. Precise stale/unavailable failures are durable receipts.
- `recoveryOf` is strict `{sourceRunId,sourceAttempt,capsuleHash,snapshotHash,normalizedExecutionHash}`. The failed source stays a failed history item; a distinct fresh run owns verification, usage and normal harvest/reconciliation. Task/Run browser views show bilingual action/cost/unavailability/lineage. Polling never submits a command.

## Source and dispatch packages

The `ExecutionPort` additions are optional methods bound through profile ownership: `readFeatures`, `savedResultSourceEligibility`, `collectSavedResultEvidence`, `readSavedResultEvidence`, `savedResultEligibility`, `settleSavedResult`, `readSavedResultSettlement`. `createCcloopExecutionPort` uses the actual Task 6 private RPC verbs, not guessed core-protocol response extensions.

Source-only input is `{source,sourceAttempt,packagePath,packageHash}`. Its strict `ccloop-saved-result-source-package-v1` manifest has `{authorityKind,source,artifacts:[{ref,file}]}` and deliberately has no admission or fence. `authorityKind` is `execution-format-failure-v1` or `legacy-published-candidate-v1`. Artifact aliases are exact archived hash-bound bytes. Archive log bytes, snapshot file bytes and raw capsule components are leaves; answer-shaped taskResult metadata never grants artifact authority.

Action StartEnvelope uses `protocol:4`, `mode:'verify-saved-result'`, `inputCheckpoint:null`, and `{savedResultRecovery:{packagePath,packageHash,admissionHash,recoveryOf}}`. Its `ccloop-saved-result-package-v1` adds the strict admission reference. `control/recovery-fence.json` is `ccloop-saved-result-fence-v1` with `{admissionHash,packageHash,runId,generation,revision,currentRunId,status:'admitted'}`. Packages, input and control parents are actual owner-0700 directories; supplied authorities are validated and never chmod-repaired; flat leaves are 0600. Defined candidate POSIX permissions belong to the producer snapshot restoration contract.

Any successful later group revision revokes the active recovery fence; unrelated group edits can conservatively abort safe verification. A2 and B revalidate current owner, membership, latest run, revision, graph/target/contract, exact claim, all four dimensions, actual caps, stop/unknown/exclusion and complete source closure. Never decorate an already dispatchable ordinary retry row: the extracted `createStartingRun` initializer writes recovery/funding/mode before INSERT and outbox.

## Admission and funding

`ccloop-saved-result-admission-v1` has `{revision,source,recoveryOf,contractHash,claim,currentRunId,predecessor,accounting,funding}`. Source identity is `{groupId,workItemId,taskId,runId,generation,graphVersion,targetVersion,executionId,envelopeHash}`. Claim is the actual `{runId,generation,commandId,ownerToken,configHash}`. Accounting is `{work,handoff,highWater,report,stopProof,settlement,receipt}`; nullable receipt/settlement are present only when supported by the actual authenticated owner ledger command.

Both funding variants use `{inheritedUsage,reservation,freshGrant,fundedTotal,historicalPolicy}`:

- `legacy-fresh-grant-v1` retains finite legacy accounting; `historicalPolicy.accountingMode:'finite-legacy'` and immutable confirmed authoredWork are distinct from actual new freshGrant. In every dimension `T=I+F`; booking charges new `V` only and does not rebook `I`.
- `optional-cumulative-v1` retains the authored cumulative ceiling, existing allowance/cap/top-up semantics and exhaustion. Current per-task mode, not group table presence, selects the branch. Nullable tokens remain nullable; non-token dimensions stay finite.

Historical policy authority is `ccloop-recovery-policy-authority-v1` with `{groupId,workItemId,taskId,sourceRunId,contractHash,accountingMode,authoredWork}`. The immutable derived-contract `confirmedGrant.work` is the authored source, not a later mutable work-item continuation grant. Reservation is `{runId,revision,workAllocationId,handoffAllocationId}`. IDs label the actual atomic reservation, using `allocation-` plus SHA256 of `{runId,revision,groupId,taskId,bucket,grant}` with distinct bucket domains. They are not a standalone allowance registry. Actual confirmed F/H allocations, full reservation and booking are checked inside admission; binding is checked again when funding is read. No ordinary optional-funded record is fabricated for legacy mode.

## Mechanical interruption and explicit no-dispatch retry

Dead-owner settlement uses the producer's exact scoped `ccloop-saved-result-settlement-v1` page, its original aliases and stop proof. Only a known positive prepared/reaped preentry or actual postentry interruption can produce `ccloop-saved-result-interrupted-v1` and an explicitly admitted saved successor on the latest same-capsule lineage. Missing entry, accept ambiguity, rejection, modification and timeout do not qualify. Unknown usage stays blocked until genuine owner settlement; authenticated charge alone cannot replace a missing interruption proof.

Orca also persists strict `savedDispatch:{state:'never-submitted'|'submitted',admissionHash,fundingHash,revision,envelopeHash}`. The first marker is created with the actual starting row; A2 fills envelopeHash, and B marks submitted durably before accept. Submitted+absent never means unspent and never automatically rearms execution.

The narrow §6.13 ordinary retry proof is `orca-saved-result-no-dispatch-v1`: `{groupId,workItemId,taskId,runId,generation,commandId,ownerTokenHash,admission,fundingHash,revision,envelopeHash,handoffRequestId,inspection:'absent',controllerState:'never-submitted',observedAt}`. It requires the authoritative never-submitted marker, actual port inspect(absent), successful known-unspent real handoff, exact inactive/current/latest run and claim, full unchanged F/H, zero booked usage and unknown flags clear. Missing proof or inspection alone cannot grant it. `resume-from-handoff` selections[] and automatic nextClaimableTask cannot convert ready recovery rows into ordinary execution. Only ledgered explicit `retry-task` consumes the proof via `savedNoDispatchConsumedBy`, marks this run failed/not-started, and authorizes a new ordinary plan/execute claim once. Held legacy full F/H is reused without double reservation; optional/different funding is refused under existing allowance semantics. Browser exposes `savedResultOrdinaryRetry` only for a validated proof and excludes positively not-dispatched rows from provider-run counts.

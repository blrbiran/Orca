## Ruling R10-1: additive schema 13

Task 10's plan named schema 11, but the reviewed Orca base is schema 12. The existing operator command scope derives its revision from `agent_preferences.revision`, so using it for installation updates would advance or rewrite unrelated preferences. Additive 12→13 creates `agent_update_state` (separate operator revision) and `agent_update_outbox` (immutable raw command/peer request plus one pending operation per operator). No old migration is rewritten. The 11→13 and 12→13 fixture tests preserve old `commands` and `agent_preferences` bytes. A separate fixture-only probe (`t10-old11-probe`, RC0) opened a schema-13 database with the immutable schema-11 reader at `f00bfdb797ee3f5de130585557fdf77dc421d535`; the reader refused `control-schema-unsupported` before opening a writer, and the SQLite bytes remained identical. This is a one-way schema upgrade; deployment of this branch would require a database backup and cannot be read by schema-12 owners. No real database was opened or migrated in this task.

## Implementation

- The configured execution port probes Task 9's `agent-installation-observe`, `agent-installation-preview`, and `agent-installation-apply` methods behind `features.agentInstallationUpdate === 'v1'`. Strict v1 observation, preview, receipt, and Orca state schemas reject malformed peer answers. The peer still owns exact configured `--agents` path, lock, re-probe, CAS, atomic replacement, intent and immutable receipt. Orca request JSON has no caller table path or shell command.
- Startup performs one bounded observation after a pending same-operation reconciliation and before listen. A read/probe failure stays visible as `failureCode`; unsupported old peers leave ordinary agent settings usable. Manual preview is owner-only and has no table write. Each candidate is explicitly selected for apply.
- Apply is owner-only at the native permission gate; member and socket Agent calls are refused before command parsing or booking, and HTTP POSTs pass the existing CSRF gate. A current command reserves its exact ID, raw hash, operator revision and peer request in SQLite before dispatch. Pending operator IDs are unavailable to other verbs and to altered same-verb payloads. Reconciliation validates raw command, immutable peer request, and any existing terminal ledger row's verb, raw hash and full outcome before closing the outbox. A matching Task 9 receipt alone finalizes command success and advances the separate update revision. A crash after receipt but before SQLite finalization replays the same operation ID and digest on reload. A proven peer stale refusal is durably booked as 409; an unsupported old peer is durably booked as 422. Neither moves the revision or leaves a pending slot. Uncertain conflicts retain the pending outbox.
- The owner can inspect pending identity after a reload and explicitly retry the same command ID. A browser also retains an unanswered envelope in session storage before sending, so a lost answer before server reservation is checked by ledger lookup rather than silently reissued. No timer or automatic duplicate apply was added. Successful apply rereads installation and selection views without reconstructing the profile router or editing frozen group/work-item bytes.

## 0. 问题

人是 agent loop 的瓶颈。但**不只是延迟上的瓶颈** —— 在 ccloop 这个仓库里，人还是裁决权本身（台账里有 126 条人裁）。

把人拿走，拿走的不止是等待时间。所以问题不是「怎么不问人」，而是：

> **哪一类决策可以先斩后奏（可逆 ＋ 有审计），哪一类必须阻塞，以及被斩掉的那些怎么让人事后看得见、翻得回来。**

### 0.1 一个必须先承认的事实

**人自述其工作方式**（本会话原话）：「我在做 ccloop 时是通过大量的反问你建议以及原因来减少我的心智负担的。」
即：在相当一部分人裁里，**信息由 agent 产出，人做的是批准**。

⚠️ **本文不对这个比例下量词。** 一份早期草稿写的是「绝大多数」——那是**未经核对的自估**：
没有人逐条读过那 126 条人裁去分类。按 ccloop 的既有纪律（「探针没被验证之前，它的输出不是证据」；
「成本只报工具给出的数，不许自估」），**这里只引人的自述，不报比例**。
若日后需要比例，做法是逐条读台账并分类，**不是估**。

⇒ 即便不知道确切比例，结论仍成立：**「不许替人宣布」保证的是【署名】，而署名不等于【判断】。**

在单任务、人能 focus 时，这条规则有效 —— 人的批准里含着真实的审查。scale 到 N 个 agent 后，同一条规则退化为
**一个带延迟的橡皮图章**：署名照旧，判断没了，延迟乘以 N。

所以它在 scale 下不是「太严」，是**失效** —— 它保护的东西已经不在了。本文第 1 节替换它。

## 1. 权限模型

```
Tier 0  机制禁止    不可逆 / 对外          agent 物理做不到（无凭证 / hook 挡死）
Tier 1  自决留痕    可逆 ＋ 能说清撤销代价   agent 拍板 → 写台账 → 人在面板异步推翻
Tier 2  不记录      纯局部                 命名、循环写法、注释措辞
```

### 1.1 两条闸门（都是机械判据，不是判断题）

**闸门 A —— 降级判据（fail closed）**

> **一个 agent 只有在能说清「怎么撤销、撤销要付什么代价」时，才可以自己拍 Tier 1。说不清 ⇒ 自动降级为 Tier 0。**

这与 ccloop 既有的 fail-closed 同形（`unlockOwnerTransferLock` 的一切拒绝都 exit 1；不可归属的锁抛出而不是吞掉）。
它落到格式上就是 §3 的 `undo` 字段：**该字段为空 ⇒ 这条决策不合法。**

#### 1.1.1 `undo.how` 必须可执行，否则这道闸门是假的

⚠️ **一份早期草稿在此处有一个双标准，必须修掉**：它以「**不可验证的自估**」为由拒绝了 `confidence` 字段（§3.5.1），
却把整个权限模型压在 `undo.cost` / `undo.blast_radius` 上——而**那两个恰恰是一模一样的不可验证自估**。
照那个写法，agent 只要在 `undo` 里写一句散文就过闸，**这道闸门只挡得住懒得写字的 agent**。

**修正**：

> **`undo.how` 必须是【可执行的命令或可机械复核的具体过程】，不许是散文。**

| 合法 | 不合法 |
|---|---|
| `git branch -f int/a <ref>` | 「把 T7 重新排进并行池」 |
| `rm -rf .decisions/run-7c.jsonl && <重跑命令>` | 「回滚一下就好」 |
| 「把契约 X 的 `targetPaths` 改回 `[...]` 后重跑 `ccloop run`」（指名到文件与字段） | 「改改配置」 |

**这样 `undo` 与 `confidence` 的区分才成立**：前者**原则上可以被执行、被核对**；后者**永远不可核**。
⇒ 校验器（§3.8）机械检查 `undo.how` 是否含可执行形式；不含 ⇒ **降级 Tier 0**。

⚠️ 这条**不会**让 agent 慎得不敢拍 Tier 1：拍不了 Tier 1 的后果是**升到人**，不是卡死。
一个连撤销步骤都写不出来的决策，本来就不该由 agent 自己拍。

**闸门 B —— 人裁的触发条件**

> **不是「agent 不确定」，而是「两个事实打架，且 agent 能把两边都摆出来」。**

「不确定」这个条件在 scale 下会无限触发，是瓶颈发生器本身。而本仓库最值钱的那几条人裁全部是「事实碰撞」形状：

| 人裁 | 触发它的碰撞（都是实测出来的） |
|---|---|
| 119 | 复用共享事件类型 **打红了两条判据** —— 两个事实不可互换 |
| 118 | **删掉一整行写入，判据照绿** —— 判据声称钉住的东西它没钉住 |
| 111 | 一个被吞掉的错误被摆上台面 —— 「已恢复」与「从未恢复」同时为真 |

这些都不是「agent 犹豫了」，是「agent 拿出了两份互相矛盾的证据」。
**这个过滤器砍掉的是量，不是价值。**

### 1.2 不确定但无冲突时怎么办

> **强制一轮自我反驳 → 自决 → 记台账。**

依据是本仓库的实测：spec 自查上一轮抓出 6 条；本轮抓出「M6 期望方向写反」这个硬错（写成"回绿"，实际应为"变红"）；
plan 自查抓出「spec 第二条未量前提没有任何一步去量它」，因而补出了 M8。
**自查是这个仓库实测有效、且不花人时间的质量来源。**

它替代的是人此前手动做的那一步 ——「反问 agent 建议与原因，引导它反思一轮」。该动作进入流程，不再消耗人的注意力。

## 2. 记录的四层分家

现行 `docs/handoff/handoff.md`（**实测 244 行 / 22454 字节**，每次开工必读）把四种东西塞进了一个文件，
而它们的生命周期与所有者完全不同。该文件开篇第一句是「⚠️ 一律自查，别信本文」—— 这是**单个 agent** 的交接文档
已经在与自己的过期作斗争。N 个并发只会把它撕碎。

| 层 | 例子（均出自现行 handoff） | 生命周期 | 所有者 | 归宿 | 写纪律 |
|---|---|---|---|---|---|
| **①项目常识** | 「本机 `rm`/`cp` 有 `-i` alias，用 `/bin/rm`」 | 数月 | 仓库 | `CLAUDE.md` / ccmem project scope | 追加 ＋ 具名 |
| **②实测值** | 「35 files / 614 tests」「红线函数 4769 字节」 | 到下一笔改动 | 一次测量 | **不存数字** | 见 §2.2 |
| **③决策台账** | —— 今天不存在 | 永久 | agent | `.decisions/<run-id>.jsonl` ＋ 索引库 | 只追加 |
| **④下一件事** | 「⛔ E1 的 I-2 与人裁 85」 | 一次交接 | **恰好一个 agent** | **ccloop 的 run 目录** | 单写者 |

**只有④才是 handoff。** 另外三层是因为"只有一个文件"才挤进来的。

### 2.1 ①层的容量纪律

路由判据是**加载方式**，不是内容：

> **`CLAUDE.md` 是无条件、每个任务都加载的；ccmem project scope 是按相关性检索注入的。**
> ⇒ **一条规则如果只在 10% 的任务里相关，它不该占 100% 的上下文。**

| 去 `CLAUDE.md` | 去 ccmem project scope |
|---|---|
| 每个任务都成立、违反了很贵 | 只在某类任务里相关 |
| 稳定（数月不变） | 随进展变 |
| 例：「验证性跑一律走 `rtk proxy`」 | 例：「Linux 上整套红 5 条」 |

**硬预算：`CLAUDE.md` ≤ 200 行。** 超了必须往 ccmem 挪，不许「再加一条就好」。
该预算须由机器检查（CI 或 pre-commit），否则必然被突破。
（实测现状：本仓库 `CLAUDE.md` 62 行 / 2567 字节，全局 `~/.claude/CLAUDE.md` 58 行 / 2201 字节 —— 两者都远未触顶，
**真正的膨胀点是 handoff 的 244 行**。四层分家本身就是①层瘦身的手段。）

### 2.2 ②层：不存数字，存可过期的观测

现行 handoff 自己写着「行号会移动 ⇒ **引用前必须现测**」「报任何字节数必须连口径一起报」。

> **既然用之前必须重测，存这个数就是纯负债。**

改存三元组：**`{ 测量命令, 上次观测值, 观测时的 commit }`**。
使「**观测时的 commit ≠ 当前 HEAD ⇒ 此值已过期**」成为**机器可判**的，而不是靠读者看到警告自觉照做。

### 2.3 ④层：run 目录已经是它

ccloop 的 `loop-contract.json` ＋ `loop-state.json` ＋ `events.jsonl` ＋ `attempts/<n>/*`
**本来就是一份机器形态的交接文档，且单写者是靠租约强制的** —— owner/lease/transfer 那一大堆代码解决的正是
「两个 agent 抢同一个交接点」。

⇒ **人读的 handoff 应当从 run 目录【生成】，而不是手写在旁边。** 手写的那份永远会和状态机对不上。

## 3. 决策台账（③层）

### 3.0 三个术语的定义

| 术语 | 定义 |
|---|---|
| **run-id** | 一次 agent 运行的唯一标识。**复用 ccloop 的 run 目录名**（`--run-dir` 的 basename），因为它已经是这个仓库里"一次运行"的既有身份，且由租约保证同一时刻只有一个进程持有它。非 ccloop 发起的 agent 需自行分配一个不与之碰撞的 id —— **该分配规则由 C 定义**，本文只要求它全局唯一且稳定。 |
| **`.decisions/`** | **仓库根目录**下的一个目录，随代码进版本库。每个 run 一个文件，**不建子目录** —— 目录层级会诱使人去"整理"，而整理就是就地改。 |
| **索引器** | 把 `.decisions/**` 读进查询库的进程。**它是只读消费者，永不回写仓库。** 谁来跑、跑多频，**由 E（面板）定义**，本文只约定它的输入形状。 |

### 3.1 并发冲突在结构上不可能发生

> **每个 agent 只写自己那一个文件，文件名是自己的 run-id：`.decisions/<run-id>.jsonl`。**

两个 agent 永远不碰同一个文件 ⇒ 即使在同一分支上，git 合并的也是**互不相交的新文件**。
**不需要锁，不需要协调，没有冲突面。**

### 3.2 不存 commit hash

直觉做法是给每条决策记一个 commit hash 字段。**不这么做**，理由有二：

1. 本仓库既有纪律已禁止此形状：「**erratum 不许引用会移动的 git 引用**（"remote tip"、"HEAD"）」。
2. 决策常常发生在 commit 存在**之前**，该字段天然可能填错。

改为：**「这条决策属于哪一笔提交」由 `git blame` 反查该行得出。**
索引器负责反查并灌进查询库；**反查时必须带 `--follow` / `-C`**，否则文件改名会切断归属。

⚠️ **早期草稿在此处写了一句绝对话（「不存、就不会错、也永不过期」），那是过度声称。准确的说法是：**

| 历史操作 | 反查还准吗 |
|---|---|
| 正常追加、`--ff-only` 合并 | **准** |
| **rebase** | **准**——归属跟着代码走，这正是想要的 |
| **squash merge** | ❌ **不准**：多笔 `bound` 被塌成一笔，「哪笔实现了它」的区分被销毁 |
| 文件改名而反查未带 `--follow`/`-C` | ❌ 断链 |

⇒ **已知缺口，不掩饰**：本方案要求承载 `.decisions/` 的仓库**不对含台账的历史做 squash**。
这是一条对宿主仓库的约束，必须在接入时明说，而不是假设。

### 3.3 事件日志，不是记录表

`.decisions/<run-id>.jsonl` 是**事件日志**，与 ccloop 自己的 `events.jsonl` 同形（Rule 11 conformance）。

决策与其落地不要求同笔提交 —— 实践中做不到。改用**后绑定**：

```jsonc
{"ev":"decision","id":"run-7c/3", ...}                    // 决策发生时写，此刻可能还没有代码
{"ev":"bound","id":"run-7c/3","note":"..."}               // 落地那笔提交里写这一行
```

`bound` **这一行本身**落在实现那笔提交里 ⇒ 「哪笔实现了它」由 `git blame` 反查 **`bound` 行**得出。
仍然不存 hash，仍然不会过期，**且不限相隔几笔提交**。

**该形状白赚两个可观测状态**：

| 状态 | 含义 | 用途 |
|---|---|---|
| 有 `decision`、无 `bound` | 已决定、未落地 | 超过阈值即泄漏，**机器可查** |
| 永远无 `bound` | 决策被放弃 | 被放弃的决策不再隐形 |

**事件类型全集**：`decision` · `bound` · `superseded`（被后续决策取代）· `overturned`（人推翻，见 §4）。
**全部只追加，任何一条都不许就地改** —— 这与本仓库的既有纪律同源（`.superpowers/sdd/**` 历史一字不改，更正另起一节；
已发布注释只能追加具名 ERRATUM）。那两条纪律当初是为「别改已发布的话」而立，但它们**恰好就是让多写者安全的语义**。

### 3.4 `decision` 事件的字段

```jsonc
{
  "ev": "decision",
  "id": "run-7c/3",
  "at": "2026-08-29T10:04:11.482Z",
  "run": "run-7c",                      // 归属（见 §6 新纪律）
  "question": "任务 T4 与 T7 能否并行",     // 在决定什么，一句话
  "chose": "串行，T7 等 T4",
  "alternatives": [                      // ⚠️ 至少一条，见 §3.5
    {"option": "并行开两个 worktree",
     "why_not": "两者 targetPaths 都含 src/persistence/fileStore.ts，合并必冲突"}
  ],
  "because": "写集相交（§5.1 判据）",
  "undo": {                              // ⚠️ 为空即非法，见 §1.1 闸门 A
    "how": "把 T7 重新排进并行池",
    "cost": "浪费 T4 已跑的 attempt",
    "blast_radius": "仅本仓库调度"
  },
  "evidence": ["git worktree add <path> main → fatal: 'main' is already used by worktree at ..."],
  "scope": "repo",                       // file | task | repo | cross-repo   → 排序键
  "kind": "scheduling"                   // 见 §3.6                          → 排序键
}
```

### 3.5 两个 fail-closed 闸门字段

| 字段 | 为空时 | 理由 |
|---|---|---|
| `alternatives` | **这条根本不是 Tier 1 决策，是一次默认行为** ⇒ 它落在 Tier 2，不进台账 | 说不出被拒绝的那一支，就没有做过选择 |
| `undo` | **降级 Tier 0**，交给人 | §1.1 闸门 A |

⚠️ **这两条与 §3.6「Tier 1 全部记」不矛盾，因为它们量的是不同的轴**：
本节判的是**「这是不是一条 Tier 1 决策」**（是 ⇒ 必记）；§3.6 判的是**「记下来之后排多高」**。
一条 `alternatives` 为空的记录不是"低位决策"，**它压根不是决策**。

### 3.5.1 为什么没有 `confidence` 字段

自报置信度是**不可验证的自估**，正是 ccloop 既有纪律所禁止的（「成本只报工具给出的数，拿不到就说拿不到，**不许自估**」）。

要判断一条决策可不可信，看 **`evidence` 空不空**、**`alternatives` 有几条** —— **这些是可核的。**

⚠️ **这条理由要成立，`undo` 就必须是可核的**，否则本节与 §1.1 是双标准。
这正是 **§1.1.1** 要求 `undo.how` 必须可执行的原因 —— **两节必须一起读，改一节就要回头看另一节。**

### 3.6 分级只管排序，不管记不记

> **Tier 1 全部记。「大方向 vs 细枝末节」是面板的排序键，不是写入的闸门。**

写一行很便宜；永远丢失一条决策很贵。排序错了随时能重排；没记下来的永远找不回来。
**这条同时化解了「上报太多人就不看」** —— 过量的成本由面板的排序吸收，而不是由人的注意力吸收。

**高位判据：这条决策有没有砍掉未来的选项。** 框架选型砍掉了它之后的所有选项；变量名一个都没砍。

`kind` 白名单（面板高位默认只看这些）：

| kind | 含义 |
|---|---|
| `dependency` | 引入 / 更换框架、库 |
| `interface` | schema、数据结构、接口形状 |
| `scheduling` | 任务排期、并行 / 串行编排（见 §5） |
| `abandon` | 放弃一条路线、改变方向 |
| `criteria` | 判据（测试）的新增或改写 |
| `boundary` | 安全 / 权限边界 |

**永不上报**：命名、格式、注释措辞、单函数内的局部重构。

排序：`scope ∈ {cross-repo, repo}` 且 `kind ∈ 白名单` ⇒ 高位；其余沉底。

### 3.7 存储：git 为真相源，DB 为索引

| | 为什么不单独用它 |
|---|---|
| **只用中心 DB** | 决策要绑 commit，而中心库里的 commit 指针会悬空（rebase、删分支、换仓库），也无法在 PR 里评审 |
| **只用 git** | 跨仓库查询（「所有项目里选了 X 框架的决策」）很难做，而面板是核心交付物 |

⇒ **两层**：`.decisions/**` 随代码进 git（真相源）；索引器把它灌进查询库供面板使用。

**非 git 目录**：`.decisions/` 照写，索引时以绝对路径 ＋ 内容 hash 代替 commit。
⚠️ **这一档确实弱** —— 没有不可变的锚点，历史可被就地改写而无从发现。**列为已知缺口，不掩饰。**

### 3.7.1 留存策略（早期草稿完全没提，是个真缺口）

一个 run 一个文件、只追加、永不改 ⇒ **N 次运行就是 N 个文件**，且纪律禁止删除。必须现在就说清楚。

**规定**：

1. **文件本身永不删除，也不合并。** 合并就是就地改，会破坏 §3.3 的追加语义和 `git blame` 归属。
2. **归档靠目录移动，不靠删除**：超过保留窗口的 run 文件整体 `git mv` 进 `.decisions/archive/<YYYY>/`。
   **内容一字不动**，`git blame --follow` 仍能反查。索引器默认只扫非 archive，`--all` 才扫全部。
3. **保留窗口由宿主仓库自己定**，本文不规定数字——因为它取决于仓库的运行频率，**估一个数就是 §0.1 批评的那种自估**。
4. ⚠️ **归档是一次 Tier 1 决策**，必须自己进台账（`kind: "boundary"`），`undo.how` = `git mv` 移回来。

⚠️ **本条的真实成本**：`.decisions/` 在仓库根目录且随代码进版本库，**每个 clone 都会带上全部历史台账**。
对高频仓库这会显著增大 clone 体积。**这是本方案已知的、未被消除的代价**，不是可以忽略的细节。

### 3.8 校验器（本 spec 唯一要求必须实现的可执行件）

一条记录合不合法**不能靠写它的 agent 自觉**——那正是本文反复否定的形状。因此台账必须配一个校验器，
它是**纯函数**：吃一行 JSON，吐 `ok` 或**拒绝理由**。

**它检查什么**（全部机械可判，无一项需要判断）：

| # | 检查 | 不过时 |
|---|---|---|
| 1 | 必填字段齐全（`ev` `id` `at` `run` `question` `chose` `alternatives` `because` `undo` `scope` `kind`） | 拒绝 |
| 2 | `alternatives` 非空，且每条含 `option` 与 `why_not` | 拒绝（§3.5：这不是决策） |
| 3 | `undo.how` 含可执行形式（命令，或指名到文件与字段的具体过程） | **降级 Tier 0**（§1.1.1） |
| 4 | `kind` ∈ 白名单（§3.6）；`scope` ∈ `{file, task, repo, cross-repo}` | 拒绝 |
| 5 | `bound` / `superseded` / `overturned` 引用的 `id` 在本文件中存在 | 拒绝 |
| 6 | 该行是**追加**——既有行一字未改 | 拒绝（§3.3 追加语义） |

第 6 项要在 pre-commit 上跑：**对 `.decisions/**` 的 diff 若含任何非新增行，拒绝提交。**
这把 §3.3 的追加纪律从"自觉"变成"机制"——与 §1 的总原则一致：**能改成「做不到」的，就不要留成「必须自觉」。**

⚠️ **校验器自身必须有变异证明**：每一条检查都要有一条"删掉它就打红"的判据。
依据是 ccloop 的实测教训——**「绿」本身可能是空的**（那个仓库实测过五次：红线函数改成永不被调用、
判据照绿；删掉一整行写入、判据照绿）。**一条检查在被看到打红之前，它不是检查。**

## 4. 人纠正的闭环

### 4.1 两份日志，各自对自己的作者权威

面板若直接写进仓库，就要求一个 Web 应用对**所有**仓库持有提交权。**安全上不给。**

| 日志 | 作者 | 真相源 |
|---|---|---|
| `.decisions/<run-id>.jsonl` | **agent** | **git** |
| `corrections` | **人（面板）** | **DB** |

**fix agent 是唯一的桥**：读一条 correction → 干活 → 在自己的提交里写 `overturned`（引用 correction id）＋ 自己的新 `decision`。

⇒ **人的推翻在它产生后果的那一刻才落进 git**；在此之前只活在 DB 里。

⚠️ **这是一处真实的不对称，不粉饰**：§3.7 的「git 为真相源」只对 agent 写的那半边成立。
**人的纠正天生诞生在 git 之外。** 一条从未被执行的 correction 只存在于 DB —— 这与「未绑定的 decision」对称，都是可查的悬挂状态。

### 4.2 correction 必须分三类

```
wrong          事实错：证据不对 / 推理断了      → 训练【验证】，不是偏好
not_my_taste   决策站得住，但人要另一个         → 训练【倾向】，喂 ccmem（子系统 B）
stale          当时对，现在不对                → 什么都不训练，重做即可
```

**这一刀必须切。** 把「事实错」混进偏好模型，会教出一个「人不喜欢正确答案」的倾向库；
反过来会把口味当成 bug 去修。

### 4.3 喂给 ccmem 的是对照样本，不是陈述

**实测现状**：ccmem 的 9918 条记忆中，来源分布为 `auto_inferred` 9612 ／ `cron_consolidated` 306，
**`user_explicit` 为 0 条** —— 它从未见过一次「人明确选了什么」。

而一条 correction 天生带着**两边**：

```
agent 选了 A（理由 R，证据 E）   ←→   人改成 B
```

**这比一条「用户偏好 B」的记忆信息量大得多** —— 它带着被拒绝的那一支和拒绝它的语境。
这就是子系统 B（倾向 track）该吃的东西，也正是它今天缺的东西。

（ccmem 的 `project_key` 实测就是 git remote URL，例如 `github.com/blrbiran/ccloop` 1353 条 ——
**与「不同项目 ＝ 不同 git 仓库」天然对齐**，跨项目聚合不需要新的键。）

### 4.4 本系统自身的成功判据

⚠️ **早期草稿把分子取成了 `overturned`，那是错的**：按 §4.1，一条 correction **只有在 fix agent 干完活之后**
才会变成 `overturned`。于是**人提了、但没人去修的那些纠正永远不进分子**——
该指标量的其实是「多少纠正被修掉了」，**而不是「多少决策是错的」**。后者才是要测的东西。

**两个指标，都要，不许混成一个：**

| 指标 | 定义 | 量什么 |
|---|---|---|
| **纠正率** | **DB 里的 `corrections` 条数** ／ `decision` 条数 | **agent 的决策质量**（你那个「约 10%」的前提） |
| **修复率** | `overturned` ／ `corrections` | **闭环有没有真的闭上**（提了的纠正有没有被执行） |

两者按 `kind`、按项目、按时间切分。**纠正率**应随 ccmem 倾向沉淀而下降；不降即说明沉淀没起作用。
**修复率**长期低，说明面板在产生人看得见却没人管的积压——那是另一种失败，且不会体现在纠正率上。

这符合 `CLAUDE.md` Rule 4（定义成功判据，循环到验证为止）：**这个系统能自己验自己。**

⚠️ 该指标有一个已知的读法陷阱：纠正率下降**也可能**是因为人看得少了，而不是 agent 变准了。
⇒ 必须与**面板的人工审阅覆盖率**（多少条高位决策被人看过）同时读，单看纠正率会自欺。

## 5. 并行编排：一条机械判据（仅判据，调度器属 C）

### 5.0 一条实测的机械事实，它砍掉一半选项

```
$ git worktree add <path> main
fatal: 'main' is already used by worktree at '.../repo'
```

**git 从机制上禁止同一分支被两个 worktree 同时 checkout。**
即使绕开（`--force`），两侧的 `git index` 是同一个文件，`add` / `commit` 会互相踩。

⇒ **并行 ⇒ 必然独立 worktree ⇒ 必然独立分支（或 detached）。串行是唯一的另一形态。中间没有第三档。**

（ccloop 现用 `git worktree add --detach`，从不占分支名 —— 这一点它已经做对了。实测：一次 attempt 跑完后
源仓库 `git worktree list` 不多出任何条目，`cleanupAttemptWorkspace` 会 `git worktree remove --force`。）

### 5.1 能否并行 ＝ 写集是否相交

两个任务能否并行，取决于**写集是否相交**。而写集**契约里已经声明了**：

- `context.targetPaths`（zod `.min(1)`，必填）
- `safetyPolicy.allowlistPaths`

这两个字段当初是为**安全**而加的，但它们正是调度器需要的东西：

> **写集 ＝ `targetPaths` ∪ `allowlistPaths`。两个任务的写集相交 ⇒ 必须串行；不相交 ⇒ 可并行。
> 机械可算，不是判断题。**

⚠️ **早期草稿在此处有一处歧义，必须钉死**：它同时列出这两个字段，判据却只写了 `targetPaths`，
`allowlistPaths` 之后再没出现——而两者可以不一致（allowlist 是 `src/**`，targetPaths 是 `src/a.ts`），
**哪个是权威没写**。
⇒ **取并集**。理由是方向性的：并集只会把「其实能并行」误判成「必须串行」，
**损失的是并行度，不是正确性**；取交集或只取窄的那个会把「其实会撞」误判成「可以并行」，**那是不安全的方向**。

加上显式依赖（T7 需要 T4 的产物），调度器持有的是一个 **DAG**：
**每个节点的 worktree 从它所有前驱的合并结果开出来。**

⇒ **上游并行任务向下游的交接物是一个 commit，不是一份文档。**

⚠️ **该判据的已知弱点**（留给 C 处理，此处只登记）：
`targetPaths` 是**声明**，不是**实测的写集**。声明得过粗会误判为相交（损失并行度，安全）；
声明得过细会误判为不相交（合并冲突或静默互坏，**不安全**）。
⇒ C 必须补一条**事后核对**：attempt 结束时用 `git status --porcelain` 的实际改动集与声明比对，不符即报。
（该数据 ccloop 已经在采 —— `scripts/claude-phase-runner.mjs` 用
`git status --porcelain=v1 -z --untracked-files=all` 采集真实改动，**不信模型自报**。）

### 5.2 合并的分档

`ccloop` 现行纪律要求**合并需人授权**。N 个并行任务每次汇流都找人，等于抵消并行收益。用 §1 的三档拆开：

| 动作 | 档 | 理由 |
|---|---|---|
| 合并进**集成分支** | **Tier 1** | 可逆：`reset` 集成分支即可；影响面只在集成分支内 |
| 合并进 **main** ／ **push** | **Tier 0** | 不可逆 / 对外，**机制上禁止 agent 做** |

`undo` 字段在前者天然填得出来（"把集成分支 reset 到 `<ref>`"），**自动通过 §1.1 闸门 A**；
后者说不清撤销代价 ⇒ **自动落 Tier 0**。**Tier 模型在此处是在实际干活，不是装饰。**

### 5.3 A′ 在编排上只承诺两件事

1. **`scheduling` 是一等的 decision kind** —— 系统自己排任务，但每一步都留痕、都能在面板上被推翻。
2. **登记 §5.0 / §5.1 的判据与其弱点**，好让 C 开工时不必重新推导。

完整调度器（队列、并发预算、DAG 执行、集成分支生命周期）**属于 C，不在本文范围内**。

## 6. 本系统新增的两条纪律

| 纪律 | 为什么现在没有它不行 |
|---|---|
| **归属**：任何持久写入必须带 `who`（run-id）＋ `when` ＋ `at-which-commit` | 现行 handoff 中存在大量**无主张**（例：「写本文时…远端含到第 12 笔」）—— **无法归因、无法复验**。单 agent 时可靠上下文猜，N 个 agent 时直接不可用。 |
| **失效**：任何被记下的实测值必须带**测量命令** ＋ **观测时的 commit** | 即 §2.2。使过期成为机器可判，而不是靠读者看到「⚠️ 引用前必须现测」自觉照做。 |

## 7. 边界声明（**必须读**）

**本文设计的是新系统的规则，不放松 ccloop 包 2 当前那一轮的任何铁律。**

E1 的 I-2 与人裁 85 那一轮**仍然完整跑在现行铁律之下** —— 尤其：

- **控制器不许 push**；开门／合并／删分支或 worktree 仍需人单独授权；

这个区分必须写死，否则本次讨论会变成一条**中途放宽规则的后门** —— 而这恰好是本文第 1 节
所诊断的那种「规则形式还在、实质已空」的失败模式。

## 9. 三个仓库的关系（**读本文前先读这一节**）

| | 是什么 | 类比 | 本文与它的关系 |
|---|---|---|---|
| **ccloop** | **一个工具**：把**单个**任务跑成「计划→执行→验证」的循环，管租约、隔离、崩溃恢复 | 一个工人 | **证据来源**。本文几乎所有实测（worktree 机制、写集字段、四层混杂、五次"空的绿"）都来自它 |
| **Orca** | **系统**：决定跑哪些任务、怎么排、并行还是串行；持有台账工具、索引器、面板 | 工头 ＋ 工地记录 ＋ 看板 | **宿主**。本文设计的是它 |
| **ccmem** | **记忆层**：沉淀人的选择倾向、项目背景、约束 | 工人与工头共用的记忆 | **接口对象**（子系统 B） |

**Orca 调用 ccloop，一个任务一个 ccloop run。ccloop 不知道 Orca 存在，也不需要知道。**

### 9.1 依赖方式：依赖，不是 submodule

- **ccloop**：已是带 `bin` 的 npm 包（`private: true`）。用 **npm 依赖**（`file:` 或 git 依赖）引入。
  **理由是锁版本** —— ccloop 正在包 2 的轮次里改动，Orca 必须能钉住一个已知为绿的版本。
- **ccmem**：**一个字都不 vendor**。它是 Claude Code **插件**（`.claude-plugin/plugin.json`），
  经 marketplace 或 `--plugin-dir` 装进 `~/.claude/`，数据在 `~/.claude/ccmem/global.db`。
  **submodule 进来它也不会运行** —— 只会拿到一份源码副本外加一个要维护的指针。**付真代价，换零收益。**
  Orca 通过它的 **CLI / DB 接口**交互。

### 9.2 台账住在哪（**最容易搞混的一点**）

> **`.decisions/` 既不住 Orca，也不住 ccmem，它住在【被干活的那个目标仓库】里。**

目标仓库可能就是 ccloop 自己，也可能是任何别的项目。
**Orca 装的是工具（写台账的库、校验器、索引器、调度器、面板），不是台账本身。**

⇒ 由此得出一条 Orca 的接入约束：**Orca 必须能对任意目标仓库工作，不能假设自己在那个仓库里。**

### 9.3 Orca 是否继承 ccloop 的 `CLAUDE.md`

⚠️ **未决，需人拍板。** 这是新建仓库唯一真实的代价：
Orca 从零开始，**不自动继承任何让 ccloop 可信的纪律** —— 没有 614 条判据、没有铁律、没有变异验证的习惯。
本文 §1／§3.8 已经把其中几条纪律显式写了进来（fail-closed、追加语义、变异证明），
但**它们目前只覆盖台账这一件事，不覆盖 Orca 的其余代码**。

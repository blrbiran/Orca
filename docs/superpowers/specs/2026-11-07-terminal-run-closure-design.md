# Terminal run closure and archive readiness (#169)

Owner: Codex controller, 2026-11-07. Source baseline: Orca `9fee12ca`; this design records choices for implementation, not a historical ruling.

## Intent

A task run whose ccloop execution has ended unsuccessfully must not remain an active reservation indefinitely. A person should be able to archive a paused group after the run's actual usage has been accounted for, while still being able to retry or verify the completed work when the group has not been archived. Neither a failed task nor a failed run becomes accepted work through closure.

## Current failure

`executionDriver.ts` step C saves a terminal report and blocks every non-succeeded run. `blockRun` leaves `runs.active=1`; `archiveGroup.ts` refuses any active run. `retry-task` can settle a known failed run while rearming the task, but a person who wants to archive, or whose authored budget has no room for retry, has no settlement action. A run with unknown usage can acquire an explicit `usageSettlement` marker, but that transaction leaves the failed run active. #172 excludes blocked runs from orchestration slots without settling them; that workaround remains valid for old owners and for genuinely blocked runs.

## Behavior

1. A new command `close-run` targets a group and names a run (`{runId}`). It refuses anonymously rather than acting automatically: the blocked state is what `retry-task`, the escalation ladder and a quota wait read, so closing on the driver's own schedule would take those exits away from a person who has not decided the work is finished. The command accepts only a current ordinary work run in `state='blocked'`, `active=1`, `drive.blockedAt='C'`, with a non-succeeded, non-null `drive.outcome`, whose work item is that run's current membership and whose run is the newest of the task. It requires the original failed terminal report, immutable stop proof and exact run identity, complete known work and handoff usage (`hasObservedUsage`, no usage event beyond `highWater`), no adoptable handoff request, and proof bytes with `ownerLeaseReleased:true` and `workerSealed:true` (the same authority as saved-result recovery). A valid explicit or approximate usage-settlement marker is accepted under its existing receipt validator; unknown or tampered usage is not inferred from remaining grant. Nonterminal blocks, success, saved-result recovery runs, other tasks' runs and groups with an open handoff request refuse by name. A repeated command on an already valid closure answers `alreadyClosed:true`; a forged marker answers `run-closure-invalid`.
2. In a single store transaction, preserve the failed outcome/report/usage/attempt identity and original grant. Write `terminalClosure` on the run: a strict proof of `runId`, `generation`, `executionId`, `highWater`, `outcome`, original `commandId`/`ownerToken`, terminal `report` artifact ref, `stopProof` artifact ref and closure time. A shared validator reopens both immutable refs, checks the report/stop proof and current usage/settlement receipt, and refuses a missing or forged field. Set `state='settled-failed'` and `active=0`, release exactly the remaining work plus handoff commitment once, mark the task allocation terminal and its work status `blocked`, and emit a named activity row. Do not charge unspent tokens or clear the historical failure. The group's used and reserved budget mirrors remain consistent. Already closed runs are idempotently skipped; a crash before the transaction may retry, after it cannot double-release.
4. A group with no other in-flight call, stop, or run can archive once its terminal runs are closed. Archive remains an explicit operation and never closes a run as a side effect. A person may pause a group first **if usage is already known**; for unknown usage the current settlement admission refuses a paused group, so settle it first, close it, then pause/archive. Handoff/shutdown stops and open handoff requests remain refused. Unarchive retains history and the normal retry/recovery gates. Cleanup may continue after closure, but the captured stop proof must show no active process owner; the physical workspace need not already be removed. If the source has an incomplete report, unknown usage without a valid settlement receipt, an open handoff request or an unobservable process, it stays blocked and the read view names the evidence or accounting step needed.
5. The run stays the task's current lineage member. `retry-task` recognizes two distinct released cases: the existing handoff settlement with a `released` usage receipt, and the new validated terminal closure. Neither releases the old remainder twice; optional and finite grants follow their existing fresh-claim reservation rules. A valid closure source may also enter saved-result eligibility without releasing the old remainder again. The unified terminal-failure candidate in `driveRecord.ts`, `systemDebug.ts`, and `webService.ts` recognizes either live `blocked/C` or `settled-failed` **with a validated closure**: ladder, quota wait, failover, probe, manual-retry racing and debug-fold ownership retain the same run identity. `blocked_waiting_human` remains exempt from automatic retry. A malformed closure proof refuses retry/recovery/read rather than being treated as an ordinary failed run.
6. `recovery list` additionally identifies terminal runs that can be closed, with the group/task/run/outcome and the next step (settle usage, close, retry, verify, archive), while keeping the existing `blockers` meaning (dispatch blockers) intact. `run show` and the Web run view distinguish 'failed work, accounting closed' from 'failed work, accounting waiting'; neither uses the word 'done'. A run with an eligible saved result still needs its independent source eligibility and funded verification command. CLI/skill show the sequence: settle unknown usage if needed, close, then retry/verify or archive.
7. Old rows are closed only when their original report/stop proof and usage evidence pass all current checks, through the same explicit command. No state-only migration, no synthetic attempt identity, and no read from a mutable target repository to fill missing historical evidence. The command never mutates the real store from a test; tests use temporary roots.

## Boundaries

- This closes the run's accounting and makes archival possible; it does not accept task work or authorize an exhausted/format-failed saved result (#163/#183/#158 are separate source-evidence work).
- Closing a known failed run is an Orca-owned deterministic operation. A person still owns settlement of a finite unknown-usage remainder. Current soft-mode approximate settlement remains limited to its existing eligibility rules.
- Keep existing protocol-3/4 ccloop output unchanged for this Orca-only change. Do not change the semantics of `usageSettlement`, whose receipt represents a charge, or call a closure proof a usage charge.

## Acceptance and negative evidence

- A failed and an exhausted run with fully observed usage and a valid terminal report become `settled-failed/active=0`; archive succeeds after pause, the original failure remains visible and no new provider work ran. Exactly one commitment release occurs across repeated rounds/restart.
- An explicit finite unknown-usage settlement or a valid Orca approximate-floor marker can precede closure; a forged marker, bad receipt, missing/changed stop proof, unobserved usage, pending event or open handoff cannot close. Failed closure does not change run/work/allocation/group budget.
- An eligible closed run with remaining authored allowance may retry; an unfunded one stays blocked and archivable. The failed run's old grant, cumulative usage and settlement remain byte-equivalent after a later retry. Ladder and quota routing still see closed terminal failures. A `blocked_waiting_human` run never enters automatic ladder.
- Transient driver blocks and active in-flight runs retain the `archive-run-active` refusal. The existing `archiveGroup.test.ts` active-run criterion remains valid.
- `recovery list` includes the blocked run with a concrete next step before closure, and no longer reports it as requiring closure after closure. The view is valid under strict client schemas.

| B：把 chain 扩为多 agent 多任务执行器 | 可直接沿用当前 Claude 启动代码 | Orca 重复 ccloop 的执行职责，与人要求冲突；不采用 |

```mermaid
flowchart LR
  U[Web 看板] --> O[Orca 任务控制与决策]
  C[CLI] --> O
  O <--> M[ccmem 决策记忆]
  O --> L[ccloop 执行与恢复]

  E --> O
```

Orca 负责 goal、任务图、授权范围、预算分配、排队、决策及纠正；确定性调度由代码完成。
ccloop 负责 agent 参数、事件解析、进程生命周期、阶段结果与执行恢复。
CLI 与 Web 调用同一个应用层；浏览器连接断开不终止后台任务。
ccmem 存储可检索的项目背景、人的偏好、决策纠正，不拥有任务状态或剩余额度。

现有 chain 保留为开发会话续接能力，先修其登记缺陷，不给它增加 Codex 启动器。
产品任务的 Codex 路径从 ccloop 接入。两条路径在迁移前分别命名、分别验收。

## 4. 任务模型与状态

四层身份：projectKey → groupId → taskId → runId。taskId 在续接中稳定，每次执行生成新 runId。
group 有 goal、successConditions、约束、预算、任务图版本和汇总检查点。
task 有目标、验收、dependsOn、写集、执行配置、预算分配和最新有效检查点引用。
run 记录实际 adapter/model、配置版本、输入检查点、用量原始证据、产物与终态。

任务状态建议：draft、ready、running、handoff_pending、paused、blocked、review、done、failed、cancelled。
依赖未满足保持待运行并展示原因；需要人的输入才标 blocked。不得靠反复重启解除同一个阻塞。
run 的终态映射保留 ccloop 原值；任务业务状态不直接替换 ccloop 的执行状态。

所有变更带 expectedRevision 和幂等 commandId。过期页面的修改返回冲突并展示最新状态。
任务领取和预算预留必须原子完成，监督进程有租约和代次；旧代次不能提交新状态或启动新执行。
保存目标工作区与产物引用，恢复前核对实际运行者和 ccloop 状态，不能只信 UI 的 running 标签。

第一阶段采用单个本地控制服务作为写入者；任务元数据存 SQLite，事务覆盖任务领取、预算和事件。
控制状态存放在显式配置的 Orca stateDir，默认仓库内被忽略的 `.orca/control/`。
源码提交不承载高频控制状态；可迁移的 checkpoint/handoff 与证据引用单独导出。
这是任务控制的新存储需求，不等于重开既有 E4 决策索引数据库优化。
所有新增全局写入必须另行登记；测试 stateDir 一律改道，继续保证真实 `~/.orca` 不被创建。

## 5. goal 拆分、依赖与运行中纠正

自动拆分输出有版本的提案：子任务、验收、依赖、建议执行配置、预算分配、理由。
代码检查重复 id、环、无效依赖、预算超配、写集冲突；模型不决定可并发执行的最终结果。
人可以编辑提案，也可为任务组预先授权范围内自动拆分。默认首次图在启动前可审阅。

运行中新增任务允许，但影响已运行任务的目标、依赖、预算改动先形成新版本。
对被影响的运行发交接请求；确认旧运行停止后再采用新版本，不原地替换工人正在执行的契约。
人的纠正先制止相关旧决策继续被派发，再按依赖影响范围标记下游需重新核验。
已经写出的代码不会因点击“纠正”自动消失；撤销、补救是有证据与授权范围的新任务。

## 6. 预算、交接与停止

区分以下量，显示来源、观测时间、未知状态，不互相换算：

- 累计 token 消耗：跨阶段与续接累计，cached input 是其中的子项，不能重复相加。
- 单会话上下文占用：用于判断是否必须换会话，与累计消耗不是同一数。
- 时间：组总运行预算、任务预算、单次执行超时；暂停时间是否计入必须在配置中明确。
  本方案以执行中的累计时长计预算；另可设绝对截止时间，不能用前者冒充后者。
- 轮数：ccloop attempt、agent turn、会话数分别命名；首版产品“轮数”指 ccloop attempt，
  会话数单独限制，agent turn 仅在 adapter 支持可靠计数时提供。
- 成本：只显示 provider 真实报告；拿不到时为 unknown，不由 token 猜美元。

组为每个活动任务预留预算，必须满足 used + reserved <= limit；拆分、重试和续接均不得重置已用量。
每份分配包含工作额度与交接预留。停止派新任务后，已运行任务仍可使用其已预留交接额度。
达到工作额度、上下文水位或最后一轮的交接窗口时转 handoff_pending，停止接新工作，写检查点并退出。
新运行只消费剩余额度；增加预算是人的显式修改，不由模型自行抬限。

adapter 能力必须显式声明：usage 是实时、阶段末或不可用；是否能请求交接、恢复、强制终止、
读取上下文占用。未知用量不能当零。仅阶段末 usage 的实现无法承诺 token 硬上限，
UI 必须展示这一限制；严格预算模式在能力不够时拒绝启动，不静默降级。
初版 Codex 只在事件实测之后声明能力，不从 exec --help 推断实时水位。

停止分三种动作：暂停派发（在飞任务继续）、交接后停止（默认）、立即终止。
立即终止可能只能保留最近有效检查点与机械采集的现场，不能显示为“完整交接成功”。
交接超时同样保存 partial 状态与原因，再由 ccloop 回收进程组。停止组时先锁存组停止状态，
阻止所有新领取，再逐个通知活动任务；重新启动必须显式清除停止意图。

## 7. 每任务 handoff 与 D3

每任务检查点是唯一恢复真相源，包含 group/task/run 身份、目标版本、已完成项、未完成项、
未决决策、awaitingHuman、预算账本引用、工作区/产物版本、验证命令和原始日志引用。
文件按 task 隔离且保留版本，不用“整个仓库最新一份”来猜本次任务该读哪份。

建议导出布局（均在显式 state/export root 下）：

```text
groups/<groupId>/checkpoint.json
groups/<groupId>/handoff.md
groups/<groupId>/tasks/<taskId>/checkpoints/<runId>.json
groups/<groupId>/tasks/<taskId>/handoff.md
```

Markdown 是从已持久化检查点生成的交接文档，不维护另一套状态；保留具体证据与恢复命令，
生成失败不使 JSON 检查点失效。用临时文件与原子替换发布 latest 引用。
组 handoff 在任务完成时归纳成果、依赖影响和未决事项，并链接任务原始检查点。
组暂停或耗尽时也更新汇总，包含未完成任务；不能等全组完成才第一次写组交接。

恢复验证身份、目标版本、产物可达性与预算；工作区有未提交变化时保存现场引用并标注，
不能把“必须干净才可写当前开发检查点”的旧约束直接照搬成产品恢复前提。
不能读取的检查点不回退到任意最新会话。历史开发 handoff 保留，D3 迁移不删除原记录。

## 8. ccmem 的决策闭环

写入记忆的单位是有出处的决策样本：原选择、理由、证据、备选、人改成什么、原因、
projectKey、适用范围及 decision/correction id。当前台账与 correction 原文仍是审计证据。
通过 ccmem 的公开 CLI/服务接口接入，不 vendor 算法，不直接写人的 SQLite。

决策前按项目与任务检索，决策记录写出引用的 memory id 和来源；必要约束来自任务契约与人的
当前指令，不允许旧偏好覆盖当前明确要求。人的纠正即时进入本任务组的有效约束，
持久记忆写入异步重试且有稳定幂等键，不能因为 ccmem 暂时失败就丢失纠正或重复写样本。
UI 展示“已记录 / 已同步记忆 / 后续已引用”，三者不可合成一个成功提示。

ccmem 不可用时显式标记 memory-unavailable。一般任务可在已知契约下继续；依赖必需记忆约束的
决策阻塞。具体公开接口与去重能力在记忆切片开工时核对，不声称当前已支持倾向 track。
验收采用改道的临时数据：记录纠正 → 同步 → 新决策检索到该样本 → 产出的选择与理由引用它。
同时测跨项目隔离、重复投递、过期偏好与当前指令冲突、记忆不可用。

## 9. Web 的首版操作面

任务组页：goal、验收、任务图、总预算、运行配置、开始/暂停派发/交接后停止/立即终止。
看板：按任务状态分列，卡片展示负责人配置、依赖阻塞、剩余额度、交接状态与待人决策数。
任务详情：目标版本、执行时间线、决策及证据、人的纠正、handoff、运行原始日志。
每项控制必须经同一个应用服务执行；前端禁用按钮只是提示，后端仍校验权限、版本、状态。
UI 不通过修改数据库字段假装执行终止完成，必须等待 ccloop 的实际终止证据。
首版保持单人本地服务；远程入口沿用并复核既有身份/Host/token 规则，不顺便引入多用户系统。

### 13.1 严格预算的执行条件（替代 §6 的能力门槛）

区分 `usageObservation`（实时／阶段末／不可用）与 `budgetEnforcement`（可封顶／软限制／不支持）。
实时用量、发停止信号和及时退出都不是 token 硬限额的证明。
严格模式只有在 ccloop adapter 能给出并执行每个请求的最大消耗边界时可启动：
边界包含输入、最大输出、内部重试与内部子调用，不允许遗漏后再用停止进程补救。
上界必须来自可验证的计量与执行约束，不能用历史均值或模型估算代替。
adapter 无法约束 agent 内部请求时，即使能读实时 usage，也只支持软限制。

每次派发前，ccloop 验证“已结算工作消耗 + 所有在途工作请求预留 + 新请求最大消耗”
不超过该运行工作额度；检查、预留与派发使用同一执行所有权。工作请求不能占用交接预留。
无法容纳下一请求时就进入交接，不等收到越线读数；交接请求同样受自己的预留上界约束。
调用结束后以去重的实际用量将预留转成消耗，释放有证据的余额。未知结算继续占用预留，
标记待核对，不能退回可用额度。实耗违反已声明上界时记录 breach 并停止新派发，不裁剪成 limit。

时间预算以所有运行的活动时长之和计费（两个并行运行各 1 分钟计 2 分钟），
另设组 wall-clock 截止时间；两者不混用。工作阶段截止点需提前留出交接和回收宽限。
attempt 在进入时扣除；同一 attempt 内交接不再虚增 attempt，若交接需要额外 attempt／会话，
其轮数／会话数也必须预留，无法预留则在更早边界交接。上限并不保证模型一定写出合格总结，
失败时仍按 partial 保存机械证据，禁止显示“完整交接”。

默认预算模式为严格；人可显式选择带限制说明的软模式，能力不足不自动降级。
初版 Codex 探针独立验收观测和封顶能力；不得把阶段末 usage 的适配器宣传成严格 token 控制。

### 13.2 所有消耗归组（补齐 §5、§6 的预算范围）

一切为该 goal 产生的模型消耗都必须有 groupId、workItemId、runId 和种类：
用户任务、自动拆分、冲突修复、交接总结、组 goal 复核、需要模型的记忆处理。
这些控制侧工作也经 ccloop 执行；Orca 不另开一个直接调用 agent 的无账本通道。
调用外部记忆服务若不能提供这次增量消耗的可执行边界，严格模式使用无模型检索／写入，
或拒绝该能力；不得隐去这部分消耗。纯代码操作不虚构 token 用量。

所有 work item 都通过同一个原子领取入口检查：组停止标志、图版本、执行所有权、剩余预算。
领取事务完成前不能调用执行器。组 `used + reserved <= limit` 用作领取不变量；
reserved 包括在途余额、交接额度和组级复核预留，结算按 §13.1 转账，不重复累计。
软模式真实超限仍如实计账，此时不变量阻止后续领取，不能靠隐藏超额维持表面成立。

创建／启动组时先预留组验收额度，再分配子任务；自动拆分本身也先领取额度。
现有 `reconcileAndLand` 直接启动额外 run、`synthesizeReconcileContract` 取双方原预算最大值
的路径必须改接统一入口，契约携带此次获批额度，不再复制原始额度。
冲突修复无可用额度时保留冲突证据并阻塞该路径；组验收无额度时保持 review，不能标 done。
停组同时阻止冲突修复、拆分和复核的新领取；已经预留的交接可继续完成。
增加预算、重试和新 run 都保留历史实耗；组最终复核失败后不得自行加预算生成下一轮工作。

### 13.3 ccloop 的交接与新运行契约（补齐 §6、§7，先于 Web 可恢复停止）

当前 `RuntimeAdapter` 只有 plan/execute/verify；当前 Orca runner 只接收 terminal status。
ccloop `resumeLoop` 只接受 planning/executing/verifying，并清理旧 attempt 后重新 planning。
因此新协议不能通过把 cancelled/exhausted 改名为 paused，或原样调用现有 resume 来实现。

新增版本化的 ccloop 公共控制协议，具体 agent 消息、事件和进程处理仍留在 ccloop：

1. 启动先传入协议版本、group/task/run、generation、commandId、目标版本、获批预算与
   可选输入 checkpointId/hash；ccloop 必须在创建 agent 前持久记录并返回 accepted。
   同 run/command 的重试只返回已有执行状态；同 id 不同配置按名拒绝。
2. Orca 发送具名 handoff 请求，含 requestId、原因、目标 run/generation 和交接期限。
   ccloop 持久锁存请求、停止新工作派发，使用已预留额度写交接候选与现场证据。
   请求被接受不等于交接完成；旧代次请求不能改变新运行。
3. ccloop 提供序号可去重的用量事件和交接结果：complete/partial/failed、候选清单及 hash、
   最后用量位置、产物快照和仍未结算的请求。它保留工作区直至 Orca 确认归档；
   不让现有成功清理或 resume 清理提前删除现场。
4. ccloop 停止相关 agent 及其受管子进程，提供执行已静止的证据；候选落盘、进程停止、
   预算结算是不同事实。Orca 按 §13.4 提交检查点后才发布 paused/可恢复。
   停止后封存最终快照与日志并重新核对候选 hash；停止前的中间候选不能冒充最终交接现场。
   超时或静止状态无法确认时按 partial/待核对展示；继续保留所有权与预算，不并发开替代运行。
5. 续接由 Orca 原子领取新 runId，固定 predecessorRunId/checkpointId/hash 和预算余额。
   ccloop 校验身份、目标版本、快照完整性，在独立工作区物化该快照并注入结构化未完成事项；
   原 run 保留原终态，不通过重置其状态或契约重置计费。换 agent 走同一任务检查点，
   原生 agent session resume 仅是适配器内部可选能力。

Orca runId 与 ccloop 执行标识建立持久映射，不假设现有 objective.taskId 就是每次执行的唯一 id。
崩溃恢复先查询持久 accepted 记录和执行所有权；启动结果不明时禁止生成另一个 run 重试。
新监督进程只有确认旧执行已停止／被隔离且无法继续写产物后，才可授权新执行。
数据库 generation 本身不能停止旧进程，ccloop 必须执行所有权检查与运行隔离。
现有原生 resume 保留原语义；未完成上述扩展的 adapter 不提供“交接后停止并续接”。

### 13.4 检查点与数据库的一致性（替代 §7“唯一恢复真相源”的含混表述）

权威划分：SQLite 的任务版本、所有权、预算账本与已提交 checkpoint 引用决定“能否执行”；
被引用的不可变检查点及证据包决定“从哪里、带什么内容恢复”。Markdown/latest 都是可重建投影。
单独发现一个 JSON 文件不能授予执行权、回滚预算或覆盖数据库状态。

每份候选含唯一 checkpointId、runId、generation、目标版本、usage 高水位、证据清单及内容 hash。
一个 run 可有多个 checkpoint，路径改为 `checkpoints/<runId>/<checkpointId>.json`，
不用 §7 的单一 `<runId>.json` 覆盖同轮历史。组汇总也保留版本，引用已提交的任务 checkpointId。

提交顺序固定：

1. ccloop 写候选；Orca 归档并核验恢复必需的快照、日志和 manifest，文件及目录持久化完成。
   文件以不可变 id 发布，不能先改 latest；未完整归档的候选不进入可恢复状态。
2. SQLite 单事务校验 generation/目标版本，按 `(runId, eventSeq)` 幂等结算用量，
   登记证据 hash、checkpointId、预算版本及运行结果，并更新任务引用和待发布投影事件。
   未结算请求保留预留；只有确认停止且不存在未决消耗，才能释放其对应余额。
3. 事务提交后才更新 latest/Markdown/Web 投影，并确认归档完成。投影失败可按事件重建；
   不回滚已结算预算，也不使完整 JSON 检查点失效。

崩溃判序：仅有候选而无数据库引用时，它是未提交候选，不能据此续跑；按运行身份核对后
重试同一个提交事务。事务已提交而投影缺失时重建投影，不重复结算／执行。
数据库引用的文件缺失或 hash 不符时阻塞恢复，不猜“最新文件”、不回退旧预算。
恢复不得释放不明在途请求的预留来换取可用额度。

迁移导出必须暂停组、确认执行静止，导出同一事务版本的控制账本快照和全部被引用证据。
导入保留 group/run 身份、已用量及未决预留；有同 id 状态时拒绝覆盖，不能只导入 Markdown
或孤立 checkpoint 作为新任务获得全额预算。跨主机恢复前必须完成源端执行权交接；
源端无法确认停止或撤销执行权时拒绝启动。导出文件的副本本身不代表第二份执行授权。

### 13.5 证据的保留与清理（补齐 §7、§9）

现有 `disposeWorkdir` 会删除成功 run 的整个工作目录，包括 loop 日志；该行为不能直接沿用。
所有有产出的运行（成功、暂停、失败或取消）在回收前必须归档：输入契约/配置版本、
原始日志、用量事件、检查点、验证输出，以及恢复所需的 Git 对象或独立快照。
脏工作区快照需覆盖已暂存、未暂存、未跟踪文件及恢复所需模式信息；仅记录路径或 HEAD 不够。
快照不完整时明确列出缺项，不能标完整可恢复。

证据放在控制服务拥有、不会随 run 工作目录删除的归档目录，引用用 artifactId/hash，
不能只指向临时目录。清理前必须从归档位置独立读回并校验，再完成 §13.4 的数据库提交。
归档失败时保留工作目录，Web 显示归档待处理；不因为 agent succeeded 就提前显示任务 done。
任务 done 还需满足原验收／落地条件；证据归档不是代码验收的替代。
工作目录清理失败只记录待清理，不重复执行已完成任务。

首版不自动删除任何被任务／组交接或决策引用的归档；后续保留策略另行设计，
不能通过清理成功任务的临时目录间接删除审计证据。任务与组 Markdown 均链接归档中的稳定引用。

### 13.6 调整交付依赖与验收覆盖（替代 §11 对切片 2/3 的顺序）

Codex 窄适配仍先做，只宣称其实际支持的调用能力；之后按以下依赖交付：

1. 任务控制底座：统一 work item/预算账本、启动幂等与所有权、证据归档、一致提交。
2. ccloop 交接协议与 D3：请求/结果/停止确认、新 run 从快照恢复、跨 run 预算继承。
3. Web 最小可运行流程：复用以上能力，交付手工任务图、启动、默认交接后停止与续接。
   Web 页面和只读展示可提前开发，但默认可恢复停止的验收必须依赖前两项通过。
4. 自动拆分与 ccmem：所有新增消耗走统一入口，完成纠正闭环和组 goal 验收。

实施计划须把下列场景转成可执行判据及对应变异；本规格不以文字检查冒充运行验证：

| 审查项 | 必须覆盖的场景 |
|---|---|
| R1 严格额度 | 首请求大于工作余额时不发出；内部重试也受限；实时 usage 但无封顶能力被拒；交接预留不被工作消费 |
| R2 全组归账 | 子任务耗尽后冲突修复不可另开额度；拆分和复核计费；停组后这些 work item 也不能领取；验收无额度不判 done |
| R3 交接协议 | 请求重复投递；接受启动后连接断开不重复启动；停止确认缺失不开替代运行；带脏快照的新 run 恢复；旧 generation 无写入权 |
| R4 一致提交 | 在文件持久化后／事务提交后／投影发布前分别中断；恢复不重复结算、不退预算；引用坏文件被拒；仅复制导出包不能获得第二份执行权 |
| R5 证据保留 | 成功清理工作目录后，任务及组详情仍能读完整日志与快照；归档失败阻止清理；清理失败不重跑任务 |

五项审查意见在本节均有设计处置。书面规格仍待人审阅；此处不把“修复问题”解释成新产品代码已获实施计划批准。

# oh-my-pi Agent Integration Design

> Initial design direction approved in conversation on 2026-10-12; this written spec awaits review. It specifies the first full Orca task path for oh-my-pi (omp) and does not claim implementation or acceptance.

## 1. Outcome and boundaries

An operator can select an installed `omp` agent in Orca's existing agent settings and run one task through ccloop's plan, execute, and verify phases. Orca must receive the same frozen selection, phase outcomes, observed token usage, failure boundaries, and standard run evidence that it receives from the existing kinds. Acceptance includes one isolated real omp task on this machine, using a locally runnable model selected at acceptance time; the model ID is never a source constant.

The first increment does not add omp skill injection, a bounded single-call estimator, OMP subagents, an interactive approval bridge, codex-only saved-result recovery, or changes to ccmem. It does not repin a production Orca service or merge/push either repository. Those release steps remain under each repository's separate authorization rules.

The owner split remains unchanged: ccloop owns agent discovery, model resolution, process execution, and phase evidence; Orca owns selection, confirmation, dispatch, and presentation. The existing `ccloop-agents-table-v1`, control capability response, and Orca agent view stay compatible. A new kind is additive.

## 2. Why this approach

Three approaches were considered:

1. **Native ccloop descriptor plus one-shot JSON adapter (chosen).** It follows the existing `RuntimeAdapter` and process/evidence lifecycle. Each phase starts a fresh `omp -p --mode json --no-session` process.
2. **Long-lived OMP RPC bridge.** It could mediate interactive permissions and reuse a session, but introduces a new recovery, framing, and approval protocol before the first task can run.
3. **Masquerade as a Claude or Codex installation.** It would avoid a descriptor but misstate capabilities and parse the wrong event format.

The chosen adapter must not assume that a successful OMP process or a plausible final sentence is a valid phase result. The ccloop controller remains authoritative for worktree state, required checks, retry decisions, and completion.

**Human scope decision, 2026-10-12:** the first increment uses the restricted one-shot CLI and isolated real acceptance. It does not build RPC-mediated tools. Extra work within an already allowed execute tool/path remains a residual risk to inspect in the pilot, not a behavior this design claims to prevent mechanically. A stricter all-actions guarantee would require a separate mediated-tool design and approval.

## 3. Installation and model selection

`omp` is discovered by the same absolute executable search and `--version` probe as existing kinds. The installed binary path comes from discovery or the operator's private agents table, never from the oh-my-pi source checkout. The new installation kind is `omp`; its strict extra fields are `defaultModel` (a canonical `<provider>/<model-id>` selector) and `profile` (a named OMP profile or `null` for `default`). The `command` must contain exactly the absolute executable and no trailing arguments. OMP-specific installation validation and adapter construction both reject extra arguments, including `--extension`, `--hook`, `--plugin-dir`, and `--config`; these could otherwise re-enable tools despite `--no-extensions`. Its context option is only `agent-default`. Capabilities declare phase-end usage observation, soft budget enforcement, unavailable context observation, durable mechanical handoff, unknown context window, and no request-bound proof. `singleCallExecution` is `null`.

Discovery reads `omp config get modelRoles --json` and `omp models --json --no-extensions` with a bounded subprocess, output size, and the candidate's effective profile/configuration environment; neither command sends a model prompt. It turns `value.default` into a canonical selector only when it exactly names one catalog selector or its bare ID matches exactly one catalog row. A fuzzy match, thinking suffix, absent role, ambiguous bare ID, missing catalog row, or failed probe is not an auto-installable default. Detect keeps the executable candidate and its observed version, sets a named `omp-default-model-unresolved` diagnostic, and omits its draft installation. Installation preview keeps an `addition` with `installation` absent: the existing Orca panel disables Apply for that row and shows its configuration-unavailable message. For an existing OMP installation's version/path candidate, preview retains the frozen default/profile and adds `unavailableReason: "omp-frozen-model-unavailable"` if the proposed binary cannot resolve that exact model. The strict ccloop/Orca preview schemas gain that optional field; the panel disables its checkbox and displays the reason. `applyAgentInstallations` rechecks the exact model against the candidate binary/profile immediately before any table write and refuses with the same named reason if it has become unavailable since preview. No other installed kind changes its draft behavior.

For the default profile the runner passes `--profile default`; for a named profile it passes the structured `--profile <name>` field, never an operator-controlled command preargument. `configDir` may be non-null only with the default profile and is passed as `PI_CODING_AGENT_DIR`; `null` inherits the worker's environment. A named profile uses OMP's profile-specific settings/auth/models paths, so the same profile is used by discovery, resolution, and every phase. OMP's generic `PI_CONFIG_DIR` root remains an inherited environment setting rather than a claim of complete configuration isolation. The installed binary's own model catalog is the source of selectable IDs on each computer; this machine's `local-litellm` entries are examples only.

The descriptor's displayed default and `resolveAgent` fallback use this installation's `defaultModel`, rather than a repo-wide constant. This requires a small descriptor hook that derives defaults from the parsed installation, used by both `tableView` and `resolveAgent`; the existing Claude/Codex hooks return their current constants. Detection and installation preview need an asynchronous OMP draft probe before building an addition, rather than their current unconditional static `draftInstallationExtras` path. A manual private-table entry with an exact default remains supported. A model override in Orca's existing operator/group/task selection wins after exact-catalog validation. The canonical selector is materialized into `AgentSelectionV1.model` when the task is confirmed and contributes to `configHash`; every phase passes it explicitly to `omp --model`. A later change to the person's OMP default therefore does not silently switch an already frozen task. Actual assistant-message `provider` and `model` are recorded separately from the requested selector for usage attribution and diagnostics.

Selection validation retains ccloop's existing nonempty, non-flag, whitespace-free, at-most-200-character model rule and additionally requires an exact selector from that installation's OMP catalog. This preserves legitimate colons and slashes inside model IDs while refusing OMP's fuzzy matching and `:thinking` selector suffix unless the entire string is itself an exact catalog ID. Thinking level is not selected by ccloop in this increment; the installed OMP configuration controls it. A configured selector that OMP cannot run fails visibly; the adapter never substitutes another model. A model supplied only by an OMP extension is unsupported because phase tool confinement requires extension discovery to be off.

## 4. Phase invocation and scope control

The OMP phase runner writes a private evidence directory under the ccloop run, starts a detached process group in the attempt worktree, registers its PID/process identity before sending the prompt on stdin, and uses the smaller of the installation timeout and remaining run time. It bounds stdout and stderr, closes and reaps the group on abort, timeout, or overflow, and preserves terminal status plus raw event evidence with private file modes. It does not use a shell to construct arguments.

Each invocation uses `--mode json -p --no-session --no-title --no-prewalk --no-extensions --no-skills --no-tools --tools <phase list> --profile <frozen profile> --model <frozen selection>`. It writes a phase-specific plain custom system prompt to a private file and passes only that file path with `--system-prompt`; the existing ccloop business prompt goes on stdin. No prompt body is an argv value. This replaces OMP's bundled default instruction block while retaining generated repository rules and its project footer. Because that footer still says completion is the stopping condition, the custom prompt defines *the task for this invocation* as this one phase and defines returning the final object as that phase's completion. It names the allowed action and explicitly stops there. It forbids independently starting another plan/execute/verify loop, retrying the whole task, dispatching an OMP subagent, or treating OMP's own completion wording as ccloop acceptance. The adapter must not rely on prompt compliance as its only boundary.

| Phase | OMP tools | Worktree rule | Final answer |
|---|---|---|---|
| plan | `read,grep,glob` | No worktree mutation | Existing `AttemptPlan` shape; plan this attempt only |
| execute | `read,grep,glob,edit,write,bash` | Changes remain subject to ccloop's target-path and controller checks | Existing complete or partial execution shape; report this attempt, do not declare task accepted |
| verify | `read,grep,glob` | No worktree mutation | Existing `VerificationResult` shape; judge the saved execution only |

The controller itself runs `requiredChecks` before the model verifier, so verify does not need a shell. The runner compares the worktree's HEAD plus tracked/untracked state before and after plan and verify. Any mutation causes a named phase failure and leaves the evidence for inspection; it is not silently reverted. For execute, the adapter records HEAD before invoking OMP and rejects any changed HEAD after the process closes, including an OMP-created commit that leaves a clean status. It then reads Git-visible tracked and untracked changed paths and refuses a result whose `changedFiles` does not exactly match; ccloop's existing path policy judges that independently matched list. The tracked-path query disables rename detection, so both deleted source and added destination must appear; a rename from a forbidden source into an allowed destination fails. This is necessary because normal ccloop execute currently gives the path policy the agent's reported `changedFiles`, whereas recovery also observes actual paths. Ignored files and host-side effects remain outside this Git-visible check. No `task`, browser, computer, network, or extension tool is intentionally enabled. Inspection of OMP 18.10.1 found that an explicit CLI `--tools` list alone does not exclude extension-registered tools; `--no-extensions` plus the binary-only installation command are mandatory. Tests must prove that the installed binary offers only the requested tools with this combination. If they cannot, the first path fails acceptance and must be redesigned.

The adapter audits OMP events before accepting a phase: any tool invocation outside that phase's named list, extension/UI request, OMP subagent activity, nonterminal `agent_end` continuation, or tool invocation after the final answer causes a named failure even if the JSON answer is valid. Plan/verify tool events must be read-only and their worktree snapshots unchanged; execute remains bound by target-path validation. The phase prompt explicitly forbids OMP from staging, resetting, committing, checking out or branching in Git; ccloop owns those operations. The adapter cannot reliably tell whether an allowed `bash` call or edit did more *within* allowed paths than the user intended. This first path does not promise to prevent every such action: its phase prompt and time limit constrain it, and the isolated real acceptance audits it, including direct Git metadata commands. If that audit observes material extra in-scope work, acceptance fails and the design must move to a mediated tool protocol before production repinning.

OMP's permission mode is not an operating-system sandbox. The execute process still has the worker's ambient filesystem and network access, just as a shell command can. The first increment therefore runs real acceptance only against a disposable target repository and redirected user-data roots. Its product boundary is the ccloop worktree, contract, tool list, and post-phase checks, not a claim of host containment. This limitation must appear in the operator-facing installation documentation.

## 5. Output, usage, and failure semantics

The adapter reads OMP's newline-delimited JSON events. It requires a clean terminal process exit, an `agent_end` that is not marked continuing/nonterminal, and a final assistant `message_end` with a successful stop reason and text answer for the phase. Each completed assistant message must report the provider and model named by the frozen selector; a silent fallback to another model is a phase failure after its usage is preserved. It validates the business object against the existing plan, execution, or verification schema. A decorated or repeated answer is handled only by the already specified conservative extraction/normalization rules; ambiguous candidates, malformed JSON, missing fields, a terminal model error, or an absent final answer fail the phase. There is no second model call to repair an answer.

Usage is accumulated from distinct completed assistant `message_end` events, never from the repeated cumulative `agent_end` payload. For each message, the four nonnegative safe-integer OMP fields `input`, `output`, `cacheRead`, and `cacheWrite` must reconcile with `totalTokens`. A normally terminated phase with complete, reconciling events receives the checked sum as exact `tokenUsage`. The existing ccloop `UsageEvidence` carries noncached input/output and cache fields; `modelUsage` groups observed spend by actual message model, sorted by model and reconciled to the phase total. OMP's reported dollar cost remains diagnostic evidence in this increment; no price is inferred from a model name and no new monetary-ledger contract is introduced. If OMP omits or corrupts usage, the phase reports usage unknown under the existing control semantics, never a synthetic zero.

On abort, timeout, torn output, or any terminal boundary that could hide a request, completed `message_end` rows provide only a lower bound. Persist that number as diagnostic evidence, but do **not** set `observedTokens` on the thrown error or pass numeric `tokenUsage` to ccloop's `settlePhase`: today's ledger treats every number as a known exact total. The phase's control usage is unknown (`null`) unless the runner can prove that no provider process/request began, in which case the existing measured-zero rule applies. A lower bound must not make an interrupted run recoverable or satisfy a budget proof.

Exit failures, timeout, abort, output overflow, process-registration failure, invalid events, invalid result, and read-only-phase mutation have distinct evidence reasons. On execute interruption, the adapter follows ccloop's existing partial-or-null contract; it does not turn a half-finished OMP explanation into successful execution. The existing controller decides retry, stop proof, recovery, and final task status.

## 6. Orca surface and rollout

Orca's existing agent list, preference editor, task override, frozen selection, driver, and usage ledger consume the new `omp` kind through the current ccloop control interface. The panel shows the per-installation default and lets the operator override it. OMP is not advertised as supporting skills; tasks with a syncskill profile continue to receive the existing `skills-unsupported-agent` refusal. Estimate and other single-call purposes see `singleCallExecution: null` and retain their current blocked-capability behavior.

The first real acceptance uses only a locally built ccloop candidate and isolated Orca/target roots. It does not update the pinned ccloop package or restart the launchd service. Publication order, if later authorized, remains ccloop release, Orca repin and service verification, then handoff. Each merge and push requires its own authorization under the repository rules.

## 7. Verification and acceptance

Tests use a fake OMP executable with JSON event fixtures and an isolated Git target. They must prove discovery and missing/bare/ambiguous-default behavior, named-profile selection, per-installation defaults in table views and previews, exact-model overrides and frozen-model reuse, refusal of fuzzy/thinking selectors, and rejection of an installation `command` carrying `--extension` or other prearguments. A version/path preview whose candidate lacks the frozen model must be visibly disabled, and Apply must recheck and refuse a model that disappeared after preview without changing the table. Tests also prove that argv contains a private system-prompt *path* but no prompt body, each phase receives the expected tool list, PID registration precedes prompt delivery, abort reaps the process group, and timeout/output failures preserve evidence. Event fixtures cover final-result parsing, multi-message usage and cache reconciliation, unknown usage, model breakdown, no duplicate counting from `agent_end`, and an interrupted completed-message lower bound that leaves control usage unknown. A deliberate fake OMP that attempts to edit in plan/verify must be blocked or detected; forbidden tool events and continuing agent events must be rejected. An execute fake that writes a disallowed path and returns a valid-looking result must not be accepted by the controller.

The real acceptance task is deliberately small: one specified file change in a disposable repository, one deterministic required check, and a tight target-path list. First prove the selected machine's provider is reachable and the chosen exact selector resolves under `--no-extensions`; a value in `modelRoles.default` or a catalog listing alone is insufficient. A short no-tool call must report the intended provider/model before any coding task starts, because OMP can silently fall back to a different available model when no explicit selector is given. Inspect the rendered system prompt and effective tools for each phase before making the paid task call. Capture the OMP event log, ccloop phase artifacts, changed paths, controller result, and Orca usage ledger. The event audit must show no mechanically prohibited action; inspect separately whether OMP independently explored, edited, tested, or retried materially beyond its assigned phase *within* the allowed tools/paths. Either kind of observed overrun fails this pilot, even if the final file and JSON answer look correct. Compare before/after snapshots of the target and redirected user-data roots. Record the actual requested selector, observed provider/model, OMP version, test command and commit, and the tool-reported token/cost values without extrapolation.

Completion requires: ccloop typecheck/build and targeted plus full test commands exit 0 with named skips reported; Orca's relevant control/panel/typecheck gates exit 0 against the local candidate; the isolated real task reaches controller acceptance with only allowed file changes, all three phase records, reconciling known usage, no prohibited event, and no material extra in-scope work in the recorded pilot. A failed real test is a diagnostic result, not a reason to loosen the acceptance criteria or repin production. Passing one pilot is evidence of that run, not proof that every future in-allowlist action is confined to the user's intended scope.

## 8. Known limits

- The local OMP provider `local-litellm` points to `http://localhost:4000`. LiteLLM's public `model_name` is `ep-20261012204110-nvhqw`, which the user identified as DeepSeek V4.1 Flash. These values describe this machine's routing, not defaults in Orca or ccloop source.
- The 2026-10-12 configuration repair changed three local fields, each after a private backup: LiteLLM's upstream `litellm_params.model` from `volcengine/deepseek-v4.1-flash` to `volcengine/ep-20261012204110-nvhqw`; OMP's `local-litellm` model ID from the upstream name to the proxy's public ep alias; OMP's `modelRoles.default` from the bare ep ID to `local-litellm/ep-20261012204110-nvhqw`. Before repair, a direct 16-token-max request to the LiteLLM ep alias returned 404 naming the wrong upstream model; a one-field temporary config returned 200; after repair the real proxy returned 200 and `OK`. Explicit and default no-tool OMP one-shot calls then both returned `provider: local-litellm`, `model: ep-20261012204110-nvhqw`, text `OK`, and no tool events. This is model-routing evidence, not yet an Orca/ccloop task acceptance.
- Before repair, a no-tool one-shot OMP call *without* `--model` completed through `deepseek/deepseek-v4-pro` rather than the intended local LiteLLM model. Its observed usage and cost belong to that other model. An adapter must never omit the frozen selector or count such a fallback as acceptance.
- The repaired custom OMP model currently reports `pricingStatus: unknown` and zero cost fields, while LiteLLM warned that its upstream model is absent from the built-in cost map. These zeros do not establish a free model or a strict money bound. Token usage remains observable; monetary treatment requires a separately verified tariff or an unknown-cost policy.
- The no-request OMP 18.10.1 RPC state probe reported exactly `read,grep,glob` when launched with `--no-extensions --no-skills --no-tools --tools=read,grep,glob`. This supports the planned read-only phase list but does not prove behavior during a model turn or across future OMP versions.
- The executable's tool restrictions and event schema are grounded in the inspected OMP 18.10.1 source and must be checked against the installed binary during implementation. Explicit `--tools` does not by itself suppress extension-registered tools, which is why this design requires `--no-extensions` and excludes extension-only models.
- A model can ignore a prompt. The tool list, phase-specific system instruction, process deadline, worktree mutation check, and controller checks limit and detect the behavior; none proves host-level containment.
- Existing soft token budgets remain soft. OMP usage and cost are observations, not a strict request spending cap.

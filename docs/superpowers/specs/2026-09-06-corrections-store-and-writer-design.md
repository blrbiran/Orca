## 3. `orca correct` 的命令表面

```
orca correct
  --repo <path>              默认 cwd。台账位置与 projectKey 都从它算
  --decision <run-id>/<n>    被纠正的那条 decision
  --kind wrong|not_my_taste|stale
  --because <text>           人的理由
  --by <who>                 默认取 git config user.name
  [--chose-instead <text>]   kind=not_my_taste 时必填（上游 §4）
  [--undo-how <text>]        与 --chose-instead 同时出现 ⇒ 走闭环
  [--again]                  同一条 decision 已被同一个 by 纠正过时，明示「我就是要再记一条」
  [--close <correctionId>]   给已存在的 correction 补闭环（同时是失败重试路径）
```

⚠️ **`--close` 与 `--decision` / `--kind` / `--because` / `--chose-instead` / `--again` 互斥** ——
那些值都已经在存储里那一行上，再收一遍只会制造两个可能不一致的来源。
给了 `--close` 又给它们 ⇒ **当场拒**。`--close` 只额外需要 `--repo` 与 `--undo-how`（见下）。
**第二轮评审发现 4。**

⚠️ **`--by` 取不到值 ⇒ 当场拒**（`git config user.name` 未设且未显式给）。
`by` 是 `min(1)`，放着不管的话会在 schema 那一层被拒，**而那条消息说的是「字段缺失」，
不是「你这台机器没配 git 身份」** —— 离原因太远。**自查发现 2。**

⚠️ **`--close` 仍然需要 `--repo` 与 `--undo-how`**：前者定位台账，后者**不在 correction 行里**
（correction 的 8 个字段不含 `undo`），所以补闭环时还得给一次。**自查发现 3。**

**两种模式由参数决定，不由 `kind` 决定**：`--chose-instead` ＋ `--undo-how` 都在 ⇒ 闭环；否则只记 correction。

⚠️ **一条必须登记的推论**：*** **闭环必须有 `chose_instead`，不管 `kind` 是什么。** ***
新 decision 的 `chose` 只能从它来。所以 `wrong` / `stale` 想闭环也得给一个 ——
**只是 schema 不逼它给**（上游裁决：被迫编造的内容不可逆）。
⇒ 这不是矛盾：**schema 管「一条 correction 合不合法」，本条管「够不够闭环」，两个不同的问题。**

**退出码**：**0** 成功 ／ **1** 输入被拒 ／ **3** 未预期异常。与 §2.2 的既有三档一致，不新增。

## 4. corrections 存储层

| 项 | 定义 |
|---|---|
| 路径 | `ORCA_CORRECTIONS_DIR` ，未设时 `join(os.homedir(), ".orca")`；文件名 `corrections.jsonl` |
| 格式 | 每行一条 `correctionSchema`（`src/corrections/schema.ts`，上游已落地，本文不改） |
| id | `c_` ＋ `sha256(projectKey \| decisionId \| at \| because \| by)` 前 16 位 |
| 写入 | 追加。写前过 schema；文件非空且不以换行结尾时**自己补一个** |
| 查重（id） | 同 id 已存在 ⇒ 拒（与台账 Check B 同形） |
| 🔴 查重（语义） | **同 `decisionId` ＋ 同 `by` 已有 correction ⇒ 拒**，消息里打印已有那条的 id；要再记一条得显式 `--again` |

⚠️ **写的是 `os.homedir()`，不是字面量 `~`** —— *** **`~` 在 Node 里不展开**，
照抄 shell 写法会造出一个名字真叫 `~` 的目录。 *** **第二轮评审发现 5。**

**`ORCA_CORRECTIONS_DIR` 不是便利，是必需**：没有它，判据会写进使用者真实的用户数据。
⚠️ **Orca 由此第一次写用户全局数据。** ccmem 为同一件事专门有一条 Rule 13；
本仓库的 `CLAUDE.md` 目前没有对应条款 —— **登记为 §9 第 6 项，不在本刀顺手改 `CLAUDE.md`。**

**id 由内容派生而不是随机**：可测、可复现，且**同一个 correction 重试时派生出同一个 id**，
这正是 §6 幂等重试的基础。含 `by` 的理由见 §7.1。

### 4.1 🔴 为什么光有 id 查重不够（第二轮评审发现 1）

**id 的派生里含 `at`，而 `at` 是「此刻」** ⇒ 人手滑把同一条命令跑两次（或以为第一次没成功），
两次 `at` 差几毫秒 ⇒ **两个不同的 id ⇒ 两条 correction 静默落盘**。
而 A′ §4.4 的修复率**分母就是 corrections 的条数** ⇒ *** **一次误操作静默污染指标，没有任何东西会报。** ***

⇒ 更坏的是它顺带废掉了一条判据：**「同 id ⇒ 拒」在现实中几乎不可能被触发**，
它只在原样重放同一行时才响 —— *** **那是一条几乎不可能红的判据**，正是本仓库一直在猎的形状。 ***

⇒ 因此加**语义查重**（同 `decisionId` ＋ 同 `by`），并用 `--again` 让「我确实要再记一条」成为
**一个显式动作而不是一次静默的副作用**。它同时把 id 查重那条判据变成真能红的
（E10 改写，见 §8）。

⚠️ **为什么不干脆把 `at` 从 id 的派生里拿掉**：那会让「同一个人对同一条 decision 写两条内容相同的
correction」在结构上不可能 —— 而那可能是合法的（时隔很久、语境已变）。
*** **fail loud ＋ 显式覆盖，好过在结构上禁掉一件未必错的事。** ***

**补尾换行这一条是抄来的，不是想出来的**：A′ 那轮实测过「结尾没有换行的台账有两个独立的坑」，
其中一个就是写入方把新记录粘在上一条后面、报成功、落盘、随后判 not valid JSON。**同一个坑不踩第二次。**

## 5. 派生表：新 decision 逐字段

闭环时那个新 run 文件里**只有两行**：`<新run>/1` 是新 decision，第二行是 `overturned`。

| 新 decision 字段 | 来源 |
|---|---|
| `ev` | `"decision"` |
| `id` | `<新 run id>/1` |
| `at` | 与 **correction 那一行的 `at`** 相同 —— 走 `--close` 时那是**上一次**的时刻，属**有意回填**，见下 |
| `run` | 新 run id（§7.1） |
| `question` | **原 decision 的 `question`，逐字** —— 问题没变，变的是答案 |
| `chose` | correction 的 `chose_instead` |
| `alternatives` | 一条：`option` ＝ 原 decision 的 `chose`；`why_not` ＝ 「人在 correction `<id>` 里推翻了它：`<because>`」 |
| `because` | correction 的 `because` |
| `undo.how` | 人给的 `--undo-how`（裁决 4） |
| `undo.cost` / `undo.blast_radius` | 原条继承，**文本里显式标注「继承自 `<原 id>`」** |
| `scope` / `kind` | 原条继承 |
| `evidence` | `["correction <correctionId>", "overturns <原 decision id>"]` |

`overturned` 六个字段按上游 spec §3 填，本文不重复。

⚠️ **`why_not` 不是 `because` 的原样复制**，而是带出处的改写。
两者说的是同一件事的两面，但 `why_not` 多带一个 correction id ——
*** **让读到这条 alternative 的人能查到它的出处，而不是只看到一句无主的理由**（Rule 13：归属）。 ***

⚠️ **继承 `cost` 的已知不准**：反方向的代价未必与原方向对称。
登记在 §9 第 3 项，**不假装它准**。

⚠️ **`--close` 路径下 `at` 是回填的，这是有意的，不是 bug**（第二轮评审发现 4）：
决定是人写下那条 correction 的时刻做的，补闭环只是把它记完整。
`overturned.at` 同口径。**读到这里觉得像 bug 的人，看的是这一句。**

**原 decision 找不到 ⇒ 当场拒**（在 `<--repo>/.decisions/` 里找），不等 `appendEvent` 的检查 5 去兜底 ——
兜底给出的消息是关于「引用解析不到」的，而真正的原因是「你给的 `--decision` 拼错了」。

## 6. 写入顺序与失败残留

| 步 | 动作 |
|---|---|
| 1 | 读原 decision（扫 `<--repo>/.decisions/` 整个目录）；拒：找不到／目标非 git／无 remote |
| 1′ | 🔴 「目标非 git」**复用既有的具名码 `target-not-a-git-repo` 与 `unlockableTargetRejection`**（`src/scheduler/preflight.ts`，本轮刚落地），**不新造第二种拼法**。依据：`planFile.ts` 与 `planReport.ts` 的注释各记着一次「同一个码手打两份、重命名一侧就产生假绿」，**这笔账本仓库已经付过**。第二轮评审发现 3 |
| 2 | **写 correction 行**（先写可修的那一半） |
| 3 | 闭环：`appendEvent(<新run>, 新 decision)` |
| 4 | 闭环：`appendEvent(<新run>, overturned)` |

**顺序的依据是可逆性**：两个存储之间不可能原子提交，所以**先写能改的那一半**。
`~/.orca/corrections.jsonl` 可重写（上游 §4.1：DB 可迁移正是它严格度低一档的理由），台账不可。

| 失败在 | 残留 | 评价 |
|---|---|---|
| 步 2 | 什么都没写 | 干净 |
| 步 3 | 一条没有 `overturned` 的 correction | *** **合法** *** —— A′ §4.4 眼里就是「未修复」那一档 |
| 步 4 | 文件里一条**孤儿新 decision**，没有 `overturned` 指着它 | 唯一难看的残留；台账只追加，删不掉 |

### 6.1 🔴 `--close` 必须是**幂等续做**，否则重试路径自己是坏的

run id 由**存储里那条 correction 行**派生（§7.1）⇒ **同一个 correction 重试必然派生出同一个 run id
⇒ 落到同一个文件 ⇒ 步 3 会因 `appendEvent` 的 Check B「duplicate decision id」直接抛。**
⚠️ **这个「必然」正是 §7.1 那条更正买来的** —— 若按初稿从命令行参数派生，重试会落进**另一个**文件，
既不会抛，也不会续上，而是**每次重试多留一条孤儿 decision**。

⇒ *** **`--close` 先检查那条新 decision 在不在文件里，在就跳过步 3、直接补步 4。** ***

这把步 4 的残留从「孤儿 decision」变成「**半完成、可续**的闭环」。

⚠️ **这是本设计里唯一一处「不这么做就一定坏」的地方** ——
不是优化，是修一条自己造出来的死路。它会单独进台账。

## 7. 并发与多用户

### 7.1 🔴 `by` 必须进 id 与 run id 的派生

🔴 *** **run id 从【存储里那条 correction 行】派生，不从命令行参数派生。** ***
具体做法：**复用既有的 `deriveRunId`**（`src/scheduler/runId.ts`），调用
`deriveRunId("fix", Buffer.from(<correction 行的规范 JSON>), <correction id>)`，
产出 `orca-fix-<hash8>` —— 那正是它现成的形状 `orca-<taskId>-<hash8>`。
*** **不写第二份派生函数** ***：本仓库已经因为「手抄一份跨模块的副本会无声漂移」收敛过一次
（`runId.ts` 自己的注释记着这件事）。

⚠️ **「从存储里那行派生」这个限定是自查抓出来的 Critical，不是措辞讲究**（§12 发现 1）：
初稿写的是从命令行参数派生，而参数里含 `at`。**重试时 `at` 是新的 ⇒ 派生出不同的 run id
⇒ 落进不同的文件 ⇒ §6.1 那条「幂等续做」当场失效**，而它正是失败重试的唯一出路。
⇒ 从存储行派生之后，`--close` 读回同一行、得到同一个 id，**幂等由构造成立，不靠自觉**。

correction id 仍按 §4 从内容派生（它是那一行自己的主键，写下时才第一次存在）。

**理由不是防哈希碰撞，是保住一条不变式**：`by` 不进派生 ⇒ 两个人对同一条 decision 各自闭环
会算出同一个 run id ⇒ **两个人写同一个 `.decisions/<run>.jsonl`**
⇒ 直接推翻 A′ §3.1「每个写入方只写自己那个文件、结构上不可能冲突」。

⇒ 由此得到一条更重要的结论：*** **台账侧不需要锁。** *** 不是因为并发少，
而是因为 `by` 进派生之后，*** **没有两个【不同的 `by`】会碰同一个文件** *** —— 与 A′ 原本的机制同源。

⚠️ *** **这条不变式到此为止，不要读得更宽**（第二轮评审发现 2）：
同一个人开两个终端、对同一条 correction 并发 `--close`，算出的是同一个 run id、落的是同一个文件。 ***
那种情况由 `appendEvent` 的 Check B（duplicate decision id）**抛错兜住** ——
*** **是「fail loud 地被兜住」，不是「被设计排除」。** *** 两者的差别在下一轮会变得要紧：
**被兜住的东西不能拿来当前提。**

### 7.2 锁只加在那一个真正共享的文件上

`${ORCA_CORRECTIONS_DIR}/.corrections-lock`，**机制照抄 `src/scheduler/repoLock.ts`**：
非递归 `mkdir` ＋ EEXIST ＋ 里面写 pid／时间的 `info` 文件。**不发明第二种锁。**

`repoLock.ts` 选 `mkdir` 而非 `flock` 的理由原样适用并抄录在实现的注释里：
*** **`flock` 在没有 `fcntl` 的平台上会静默退化成 no-op，而 Rule 12 不允许静默退化。** ***

### 7.3 但**不与 `repoLock.ts` 合并**，理由是语义真的不同

| | repo lock | store lock |
|---|---|---|
| 覆盖 | 整轮（分钟级） | 一次追加（毫秒级） |
| 拿不到时 | 拒绝整轮，合理 | 应**短暂重试**，而不是让人重打命令 |
| stale 回收 | 明确不做（"deliberately out of scope"） | 若也不做，**一次崩溃就把所有人的 corrections 永久锁死** |

⇒ store lock 的做法：**短退避重试，总上限约 1 秒；超时 ⇒ 具名拒绝 `corrections-store-busy`，
消息里给出锁目录路径与 `info` 的内容（pid、取锁时刻）。**
*** **不做 stale 回收、不猜它死没死** *** —— 立场与 `repoLock.ts` 一致，只是给人一条可执行的出路。

⚠️ **合并两者会把两组不同语义塞进一个函数，再参数化出一堆开关。不合并是有意的，理由在此，不是疏忽。**

### 7.4 已知限制：跨机共享文件系统

*** **`mkdir` 的原子性在 NFS／SMB 上历来不可靠。** ***
「多用户」若落地成**共享存储**而不是同机多进程，**本设计的互斥不成立**，
到那一步必须换底座（SQLite WAL 或服务端），**不是加重试能补的**。
⇒ 登记在 §9 第 5 项。**本文不假装覆盖了这种形态。**

### 14.1 C1 ＋ I8 ＋ I9 —— 闭环从「两次追加」变成**一次落盘**

**现测**：`appendEvent` 一次只吃一个事件，做一次「整份文件 ＋ 这一行」的前瞻校验，然后**一次 `appendFile`**；
注释写明「流式写入方看不见还没追加的行，所以 `overturned` 写在它的 `decision` 之前会抛」。
⇒ *** **§6 那条孤儿 decision 的残留，完全是「拆成两次追加」造出来的。** ***

**处置**：新增 `appendEvents(decisionsDir, runId, events)`，闭环走
`appendEvents(…, [新 decision, overturned])`。契约：

- 逐条过 Check A 与 `validateLine`；
- Check B 同时查**批内**与**批与文件之间**；
- 补尾换行的 separator 只在**整批最前面**加一次，批内各行之间是 `\n`；
- 前瞻校验拿 `existingText ＋ 整批 payload` 一起过一次 `validateFile`；
- **一次 `appendFile`**；
- **空批当场抛错**（否则 payload 就是那个 separator，会往无尾换行的文件里追加一个孤立的 `\n`）。

**第二席对这条契约的现测复核（接受）**：`validateFile` 的 `fileDecisionIds` 从**整份预期文本**重建
⇒ 批内 `overturned.replacedBy` 指向批内 decision **解得开**；`overturned.id` 指向别的文件里那条原 decision，
由扫兄弟文件建出的 `externalDecisionIds` 解开。*** **「检查 5 自然解得开」是核过的，不是假设。** ***

**由此结构性消掉三条**：I9（产生孤儿 decision 的那一步不存在了）、I8（不再需要「续做」）、
C1（第二次 `--close` 落进同一个文件 ⇒ 撞 Check B 抛错，坏结果从「静默落两条」变成「响亮拒绝」）。

⚠️ *** **诚实登记：这不是「写入变原子了」。** *** `appendFile` 对任意长度不保证原子，一次断电仍可能留下半行 ——

#### 🔴 幂等检查必须是**分支无关**的（第三席）

初稿的检查是「**这个工作树里的**台账文件里有没有带这个 `correctionId` 的 `overturned`」。

⇒ **改成两问**：*** **(1) 工作树里那个文件有没有；(2) `git log --all -- <path>` 有没有提交过它。** ***

*** **第二次 `--close` 必须落进【同一个】文件，才撞得上 Check B。** *** 若从命令行参数派生，

现测 `repoLock.ts` 注释明写 stale 回收 **"deliberately out of scope"**；`run.ts` 把 `release()` 放在 `finally` 里正因如此。
第一版把释放写成末步，而它前面全是**预期会发生**的拒绝。
*具体场景*：人被语义查重拒（「你已经纠正过这条」）⇒ 进程带着 `<repo>/.git/orca-lock` 退出
⇒ **此后该仓库每一次 `orca run` 都被挡**，直到有人手工删掉那个目录，而 orca 从不说这条出路。
⚠️ **§7.3 那张表里控制器自己写过「stale 回收若也不做，一次崩溃就把所有人的 corrections 永久锁死」——
它把这条道理用在了 store 锁上，却没回头套用到 repo 锁。**

#### §7.1 那句「台账侧不需要锁」的替换

| 机制 | 管哪一格 | 还成立吗 |
|---|---|---|
| run id 是**整条 correction 行**的函数 | **两个 `correct` 之间** | **原样成立**（措辞见 14.11） |
| **repo 锁** | *** **`correct` 与 `run` 之间** *** | **新增** |

⇒ **两条机制各管一格，不互相替代。** 上文那句错在**框架太窄** —— 它只考虑了 `correct` 对 `correct`。

#### §7.3 那张对照表补一行

| | repo lock | store lock |
|---|---|---|
| **谁持有** | `orca run` 全程；**`orca correct` 的闭环模式**（只记模式不取） | **只有 `orca correct`**，且只在临界区内 |

*** **取序定死：先 repo 锁（外层）→ 后 store 锁（内层）。** *** `orca run` 永不取 store 锁 ⇒ **不成环**。

### 14.4 C4 —— `--close` 的互斥从「一律拒」收窄成「条件拒」

**缺陷**：§3 同时声明了三件不能同时成立的事，而 `correctionSchema` 让 `chose_instead` 除 `not_my_taste` 外可选
⇒ 任何以只记模式记下的 `wrong`／`stale`，**闭环路被彻底堵死**，且失败在 schema 深处。

**处置**：

- `--close` 与 `--decision` / `--kind` / `--because` / `--again` **一律互斥**（那些值都在存储行上）；
- `--chose-instead` **条件互斥**：**当且仅当存储行里没有它时**允许同时出现；行里已有 ⇒ 拒；
- 🆕 **`--undo-how` / `--undo-cost` / `--undo-blast-radius` 与 `--close` 【不】互斥**（第三席的 out-of-brief）——
  *** **这三个字段本来就不在 correction 的 8 个字段里**，`--close` 拿不到它们，所以它们必须能一起给。 ***
- 新增具名拒绝：**存储行没有 `chose_instead` 且命令行也没给 ⇒ 在任何写入之前拒**。

#### `--close` 补给的 `chose_instead` **不回写** correction 行

理由：回写要引入「就地重写 JSONL 某一行」这套今天没有第二个用途的机制；
且事后往一行里补字段会让「这一行何时写完」不可知 —— 正是 C5 抱怨的那种污染。

⚠️ **可逆性要写准**（第二席 I-K）：初稿写「可逆」说得太满。台账**按仓库分散**，
而这个存储做成用户全局的全部理由就是跨项目聚合 ⇒ 回填要求当时那 N 个仓库的 clone 都还在、且分支上有那笔提交。
⇒ 改写为 *** **「条件可逆：仅当那个仓库的 clone 与该提交仍可达」** ***，登记 14.19 第 9 项。

⚠️ **为什么不采纳「把 `chose_instead` 塞进 `overturned` 的 passthrough 字段」**：
那要给第一条真 `overturned` 加一个**上游没定义的第七个字段**，而 §0 明写「形状本文一个字都不改」，
且 `overturned` 是**不可逆的那一侧**。*** **用不可逆的一侧去买可逆一侧的方便，方向反了。** ***

### 14.5 C5 —— 两个 `at` 都写**真实落笔时刻**

*** **§5 那整段「回填是有意的」（含「读到这里觉得像 bug 的人，看的是这一句」）作废。** ***

1. 上游 §3 把 `overturned.at` 定义为「落笔时刻」，「与 `decision.at` 同口径」
   ⇒ 回填是**下游文档在一个只追加字段上悄悄推翻上游裁决**：形状没变，**含义**变了。
2. **它什么也没买到**：correction 的 `at` 本来就能通过 `correctionId` join 到。
   被毁掉的是「这一行何时被写下」这个唯一记录，且经 `--close` 写入的行与直接写入的行**再也无法区分**。

⇒ 判据 E16。⚠️ **它与 14.1 那个分支无关的幂等检查是配套的** ——
真实时刻意味着两次写入逐字节不同，**所以幂等检查绝不能只看工作树**。

### 14.6 I1 —— 语义查重的键补上 `projectKey`

**键从 `(decisionId, by)` 改为 `(projectKey, decisionId, by)`。**
decision id 不带仓库标识，而且是**派生的**（`deriveRunId("round", planBytes, base)`）
⇒ 同一份 plan 在同一个 base 上得到同一个 round id ⇒ 同样的 `<run>/<n>` 会出现在任何 clone 或 fork 里
⇒ 一个人在两个仓库里纠正同一个 decision id 会得到**假的「已经纠正过」**，被推去用 `--again` ——
*** **而 `--again` 会把整道守卫关掉。** ***

### 14.7 I2 —— 查重的读与追加必须在同一次持锁内

*** **「取 store 锁 → 读 → 判 → 追加 → 释放」是一个临界区，释放写在 `finally` 里。** ***

⚠️ 🔴 **夹具的三个硬约束**（第二席 I-B ＋ 第三席）：

1. *** **不能用同一个 `--repo` 的闭环模式** *** —— 外层 repo 锁已经把它们串行化了，第二个进程走不到 store 锁那一格。
   ⇒ 用**同一 remote 的两个 clone**，或**两个只记模式进程**（它不取 repo 锁）。
2. *** **barrier 只能是【单边】的** *** —— 未变异的实现里，读在锁内，**两个进程不可能同时越过读**，
   双边会合的 barrier 会把正确实现挂死。⇒ 让 P1 持锁并 sleep。
3. 🔴 *** **P1 的 sleep 必须【短于】store 锁的超时上限** *** —— 否则未变异的那一趟是被超时（exit 4）放过的，
   **而不是被查重拒绝放过的**：判据会「因为另一个理由而绿」。断言要点名 P2 拿到的是**查重的拒绝消息**。

### 14.8 I3 —— store 锁的父目录必须先递归建

`repoLock.ts` 的非递归 `mkdir` 安全，是因为父目录 `<repo>/.git` **保证存在**；`${ORCA_CORRECTIONS_DIR}` 不保证
⇒ 新机器上第一次跑就得到 `ENOENT: … mkdir '/Users/x/.orca/.corrections-lock'` ——
正是提交 `fix(run): name a target that cannot hold the repo lock…` 刚偿清的形状。
**处置**：父目录 `mkdir(dir, { recursive: true })`；**锁目录本身保持非递归**（那是承重的）。

⇒ 记法：*** **「机制照抄」时必须把它的【前提】一起抄过来核一遍。** ***
⚠️ **本节自己违反过这条两次**：第一版把预检排到锁后面（第二席 I-A）、第二版没跟着放宽提交的状态守卫（第三席）。
*** **知道一条记法，不等于会用它。** ***

### 14.22 两个「从没被独立视角检验过」的框架

第一席**没有**攻这两条，控制器当时登记了「评审员没提 ≠ 被检验通过」。第二席被点名去攻，**两条都攻出了东西**。

#### JSONL vs SQLite（§1 裁决 2）—— **裁决保留，理由换掉**

原理由的 **(a)**「放进目标仓库会推翻 `projectKey` 的存在理由」*** **论的是【放在哪】，与【什么格式】无关
—— 不能计入这个分叉的一票** ***；真正的论据只剩 (b)（native 依赖／`--experimental-sqlite`）。
而选了平文件之后长出来的是：mkdir 锁 ＋ 退避 ＋ 超时、两个新退出码、读全文的临界区 ＋ 一条要两个 clone 才能红的并发判据、
补尾换行、文件权限、以及 14.4 那条「不做就地改行」的裁决。**一个事务能一次买下前三样。**
§7.4 自己也写着「多用户若落地成共享存储……必须换底座（SQLite WAL 或服务端）」。

⇒ **保留裁决，换掉理由**：真正的支撑是本仓库自己的原则（`corrections/schema.ts` 的注释）——
*** **严格度跟着可逆性走。** *** corrections 是**可迁移的那一半**（格式选错是一次迁移），
台账是**选错就永远修不掉**的那一半。**把评审预算压在存储格式上，本来就是投错了地方。**
⇒ §1 裁决 2 的 (a) **从这个分叉的论据里划掉**。

#### 机械派生 vs 问人（§1 裁决 3）—— **12 行里 10 行活得下来**

活得下来：`question` 逐字、`chose` ← `chose_instead`、`because`、`evidence`、`id`／`run`／`ev`。

*** **活不下来的是继承来的 `undo.cost` 与 `undo.blast_radius`。** ***

### 14.24 §3 的模式判定改写：**表达了闭环意图，就不许半途**

§3 原文写的是「**两种模式由参数决定，不由 `kind` 决定**：`--chose-instead` ＋ `--undo-how` 都在 ⇒ 闭环；否则只记」。

🔴 **第三席指出这条推断有一个静默降级**：*** **人把 `--undo-how` 打错一个字母，命令不会拒绝 ——
它会安静地变成【只记模式】、写下一条 correction 行、然后 exit 0。** ***
人以为自己闭了环，实际台账一个字都没写，而**没有任何东西会告诉他**。

⇒ **改写为**：

*** **给了 `--chose-instead` 与 `--undo-how` 中的【任一个】，就算表达了闭环意图；
此时缺另一个 ⇒ 具名拒绝，消息说清缺的是哪一个。两个都不给，才是只记模式。** ***

**为什么不新增一个显式的 `--close-loop` 开关**：意图已经由那两个参数表达得很清楚了，
多一个开关是多一件要人记住的事；而这条改写零新增词表。

**为什么这条值得改**：这条路的产物是**不可逆的台账写入**。
*** **在一条不可逆的路上，把一次拼写错误变成一次语义降级，代价太高。** ***
⇒ 判据 **E3** 钉它，变异是「让缺失回落成只记模式」（**即第二版的行为**）。

### 15.3 落地的是**三条**，且**三条各有各的理由**

实现在 `src/corrections/gitState.ts` 的 `midOperationRejection`，其 doc comment 是本节的代码侧副本。

| 拒 | 理由 |
|---|---|
| `MERGE_HEAD` | **git 自己拒**（上表，exit 128） |
| `CHERRY_PICK_HEAD` | **git 自己拒**（上表，exit 128）。⚠️ 这正是 §14.3 那条 Critical 的来源：只拦「merge／rebase／detached」会让它整个漏过去 |
| **detached HEAD** | *** **不是因为 git 拒（它不拒）。** *** 那笔提交**不在任何 ref 上**，而幂等检查是 `git log --all -S<correctionId> -- <path>`，**`--all` 看不见没有 ref 指着的提交** ⇒ 下一次 `--close` 会答「还没闭环」，往**只追加**的台账里**再写一对行** |

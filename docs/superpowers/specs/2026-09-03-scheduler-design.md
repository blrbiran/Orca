## §0 三条总原则（**先读这节，后面每一节都在用它**）

### 0.1 凡是 C 够不着的动作，只能检测 ＋ 降级，不能声称禁止

同一个形状在本设计里出现了**三次**：

| # | 「你无法禁止……」 | 于是主干是 |
|---|---|---|
| 1 | 禁止 agent 在执行任务时改哪些文件 | **冲突处理**（§5），写集判据只是优化 |
| 2 | 禁止写集判据算错 | **判据算错时系统必须仍然正确**（§3.4） |
| 3 | 禁止人在合 PR 时 squash | **台账在归属被销毁后仍然可用**（§8.4） |

⇒ **声称禁止，就是把一条不成立的前提写进设计。** 本文任何一处写「禁止」，都必须能指出
**是什么机制在禁止**；指不出来的，一律改写成「检测 ＋ 降级」。

### 0.2 判据算错是常态，不是异常

第 1 条的直接推论。写集是**基于声明的预测**：既不可强制（ccloop 的 `evaluatePathPolicy` 是
**纯事后检测器**，调研 §5 第 3 条现测），也常常不准。

⇒ **不允许任何一条代码路径以「判据说不会撞」为前提做简化。**

### 0.3 一条判据在被【看到】打红之前，它不是判据

来自 ccloop 的实测教训（五次「绿是空的」）。本文每新增一个分支，都要在 §10.3 点名
**那条删掉【它自己】的变异**，并确认它存在且被看见红。

## §1 范围与非目标

### 1.1 C 是什么

> **一个一次性进程**：吃一份任务图，把每个任务交给 ccloop 跑一遍，把结果整合进一条工作分支，
> 处理途中的冲突，把替人做的每个选择写进**目标仓库**的台账，然后退出。

**不是** daemon、不是队列服务、没有 DB、没有 HTTP、没有 UI。一次 `orca run <plan>` 跑完就没了。

### 1.2 六条硬边界（**明写，不默认**）

| # | 边界 | 理由 |
|---|---|---|
| 1 | **单机** | ccloop 的崩溃检测假设 PID 是本机的；跨主机没有协调原语。hermes 自陈同款理由（`kanban.md:1165`） |
| 2 | **单进程编排器，分层推进** | 汇流点明确 ⇒ 事后核对／合并／冲突处理有地方挂 |
| 3 | **同一目标仓同时只允许一个 orca 进程**，用锁强制；**抢不到就报错退出，不静默降级** | 工作分支是共享可变状态。借鉴 6 **反着借** —— hermes 在无 `fcntl` 的平台把锁退化成 no-op，Rule 12 不允许 |
| 4 | **不重造租约／心跳／崩溃检测** | ccloop 已有整套。**liveness 归 ccloop** |
| 5 | **不用模型做路由** | Rule 5。模型只在 §5 做冲突分类与和解 —— 那是 Rule 5 明列该用模型的 `classification` |
| 6 | **v1 全程跑在一次性沙盒仓 ＋ `scripted` adapter** | 不花 claude 的钱 ⇒ 判据能反复跑。**这也是一条限制**，见 §10.4 缺口 1 |

⚠️ **§1.2 第 4 条的一处具名更正**（本文 §6 现测所致）：
先前草稿写的是「**C 只看子进程退出码**」——**那是错的**。ccloop 的 `run`/`resume` 是
`finalState.status === "succeeded" ? 0 : 2`，**四个非成功终态被压成同一个 2**。
⇒ **C 必须读 `<runDir>/loop-state.json` 的 `status`。** 更正的是「怎么知道结果」，**不是「谁管存活」**。

### 1.3 明确不做

面板（E）／倾向 track（B）／检查点交接（D）；**自适应并发预算**（借鉴 12，Zuul Pipeline Window ——
v1 用固定上限）；常驻 dispatcher ＋ SQLite ＋ REST；tenant／多 board／通知／`scheduled_at`；
**用 LLM 工具调用终结 worker 生命周期**（hermes 那套，Rule 5 禁止 —— ccloop 的退出码已是确定性等价物）。

### 1.4 怎么调用 ccloop：**spawn 子进程，不走 npm 依赖**

A′ §9.1 写的是「npm 依赖，锁版本」。**那条当前没有可执行形式** —— 调研 §5 第 6 条现测：
ccloop 的 `package.json` 是 `private: true`、`bin` 指向 `dist/cli.js`（要先 `npm run build`）。

⇒ **v1 改为 spawn 子进程**，二进制路径由 plan 文件给出。三条理由：

1. 它是「liveness 归 ccloop」的自然形式 —— 走 npm 依赖会诱使人 `import` ccloop 的内部函数，
   把存活责任偷渡回 C；
2. 不需要动 ccloop 的发布形态；
3. **锁版本的诉求另有办法满足**：每次 spawn 前记 ccloop 的 `git rev-parse HEAD` ＋ `--version`，
   **写进台账的 `evidence`**。锁的是「这一轮跑在哪个 ccloop 上」这个**事实**，而复现时需要的正是它。

⚠️ **这是对已发布 spec 的一处具名偏离**（A′ 不就地改）⇒ 由本文承接，并进台账（`kind: dependency`）。

### 1.5 🔴 一条硬前置：ccloop 必须先能交出 commit

见 §4.4。**这不是"更干净"，是 v1 跑不起来**（`scripted` adapter 不产 `diffPatch`，§4.4 现测）。

## §2 任务图与两层身份

### 2.1 两层身份（借鉴 1，🔁 hermes ＋ Airflow 独立收敛）

A′ §3.0 要求 run-id「**全局唯一且稳定**」——**这两个要求内在打架**。两层身份把它解开：

| 身份 | 是什么 | 谁给 | 重跑时 |
|---|---|---|---|
| **`taskId`** | DAG 节点 | plan 文件，人写 | **不变** |
| **`run-id`** | 一次 ccloop 运行 ＝ run 目录 basename | **C 分配** | **每次新的** |

台账的 `run` 字段填 run-id；「这是哪个任务」由 run-id 里编码的 taskId 读出。
**这是对 A′ §3.0 的一处具名澄清**，进台账。

### 2.2 run-id 分配规则（A′ 明确甩给 C 的洞）

A′ §3.1 的保证——「每个 agent 只写自己那个文件 ⇒ **结构上不可能冲突**」——**整个压在 run-id 不撞上**。

```
基础 id = orca-<taskId>-<hash8>     hash8 从「契约文件内容 + 基点 commit」导出
分配    = mkdir(<runsDir>/<id>)     ← 非 recursive
          EEXIST ⇒ 换 <id>-2、<id>-3 … 重试
```

**用 `mkdir` 的原子性做仲裁，不引入 DB**（借鉴 17，🔁 nextflow ＋ hermes 收敛到同一原语）。

#### 2.2.1 一条现测，它砍掉了一层本来要加的目录

**观测时点 2026-09-03，ccloop HEAD `0f7fc28e8bdc573ba22840d3c7e00e25d8927b17`**，
口径 `sed -n '45,80p' src/persistence/fileStore.ts` 整份读回：

`ensureFreshRunDir`（`src/persistence/fileStore.ts:50`，唯一调用点 `initializeRunFiles:75`）——

1. 它自己就是 `mkdir(runDir, { recursive: true })` ⇒ **一个已存在的【空】目录不会被拒**；
2. 拒绝条件是目录里已有 `loop-contract.json` / `loop-state.json` / `events.jsonl`，
   或 `attempts/`、`worktrees/` **非空**，报错逐字：
   `runDir already contains prior run data (<label>); V1 does not support reinitializing an existing automated run`

⇒ **C 先 `mkdir` 占位不会与 ccloop 的前置条件打架** ⇒ 原打算加的 `.claims/` 旁路目录**砍掉**。
⇒ 且 `EEXIST` 递增**同时覆盖两种情况**：id 被本轮占了、或上一轮跑挂留下带数据的目录。

### 2.3 plan 文件的形状

```jsonc
{
  "targetRepo":    "/abs/path/to/repo",
  "ccloopBin":     "/abs/path/to/dist/cli.js",
  "runsDir":       "/abs/path/to/runs",
  "workBranch":    "orca/w/<name>",
  "policy":        "local-merge",
  "ledgerMode":    "in-repo",
  "tasks": [
    { "taskId": "T1", "contract": "/abs/path/t1.contract.json", "dependsOn": [] },
    { "taskId": "T2", "contract": "/abs/path/t2.contract.json", "dependsOn": ["T1"] }
  ]
}
```

**六条当场拒**（全部机械可判，各配点名变异）：

| 拒 | 理由 |
|---|---|
| 任何**相对路径** | 借鉴 7：相对路径会对着编排器**恰好所在的 CWD** 解析 —— 既有歧义，又是 confused-deputy 逃逸面 |
| `taskId` 重复 | 人会写重 |
| 图**有环** | 输入 bug，**不试图修** |
| **契约文件落在 `targetRepo` 之内** | 见 §2.4.1 |
| 🔴 **`workBranch == default branch`** | 见 §4.2 |
| **`policy` 不是 `local-merge`** | 见 §4.2 |

### 2.4 图的构造与分层

**边 ＝ 显式 `dependsOn` ∪ 隐式（写集相交，§3）。** 分层用 Kahn 拓扑排序，层内并行。

⚠️ **隐式边没有天然方向** —— 谁先谁后是**任意的**，而结果依赖这个任意选择
（借鉴 13：bazel／buck2／snakemake／pants 四个系统撞了**都让人裁**）。
⇒ **调度器不许静默替人挑这个顺序**：它是一次 `scheduling` 决策，进台账、带 `alternatives`、能被推翻。

#### 2.4.1 为什么 v1 不做「认领那一刻重算写集」

借鉴 3（hermes `claim_task`，`kanban_db.py:4643`）要求在真正 spawn 前重算。**v1 不做**，
换成一条**可机械强制的前提**：

> **契约文件必须落在 `targetRepo` 之外** ⇒ 上游任务改不到它 ⇒ 写集在图构造时算一次就够。

⚠️ **这条前提是承重的**：契约文件一旦进目标仓，本节就塌。所以它是 §2.3 的**当场拒**，
不是注释里的假设。「认领时重算」登记为 v1 之外。

### 2.5 已知的薄处

- **内容导出 id 在 v1 是一笔预付，不是已兑现的收益**：它的价值是让 resume 在 v2 可能
  （nextflow 的 resume 正是靠它），而 **v1 不做 resume**。代价接近零所以付了，**但不许写成好处**。
- 而且基点在分层执行中会变（每层合并后 HEAD 就动），所以准确的性质是
  「**同契约 ＋ 同基点 ⇒ 同 id**」，比「同契约 ⇒ 同 id」弱一档。

## §3 写集与相交判据

### 3.1 写集的定义

> **写集 ＝ `context.targetPaths` ∪ `safetyPolicy.allowlistPaths`**（A′ §5.1 原样）

取并集的理由是**方向性**的：并集只会把「其实能并行」误判成「必须串行」——**损失并行度，不损失正确性**；
取交集或只取窄的那个会把「其实会撞」误判成「可以并行」，**那是不安全的方向**。

⚠️ 但要读准它今天的强度（调研 §5 第 3、4 条现测）：**这两个字段一半 ccloop 从不检查
（`targetPaths` 根本没被 `evaluatePathPolicy` 读），另一半只事后检查。它们不是闸门。**

### 3.2 「相交」的定义 —— 朴素集合求交是错的

A′ §5.1 只写「相交」，**没定义什么叫相交**。路径上它不是集合求交：
`src/` 与 `src/a.ts` 朴素求交是**不相交**，而那正是 A′ §5.1 自己标记为**不安全**的方向。

按借鉴 8（buck2 `registry.rs:125` `claim_output_path`；bazel `ARTIFACT_PREFIX_CONFLICT`）：
**目录字典树插入，三种冲突**——

| | 形状 | 给人看的话 |
|---|---|---|
| **① 相等** | 两边认领同一路径 | 「T1 和 T2 都要写 `src/a.ts`」 |
| **② 新 ⊃ 旧** | 新路径是目录，底下已有别人的叶子 | 「T2 要写目录 `src/`，里面已有 T1 的 `src/a.ts`」 |
| **③ 新 ⊂ 旧** | 新路径穿过一个已被认领的叶子 | 「T2 要写 `src/a.ts`，它在 T1 认领的 `src/` 里」 |

**冲突时列出全部冲突路径，不是只报第一条。**

⚠️ ② 与 ③ **计算上是同一条判定**（前缀关系），**诊断上不是**（人拿到后的修法不同，buck2 也分开报）。
⇒ **共用一条判定，保留两个名字** ⇒ **变异要点在判定上，不是点在两个名字上**，
否则会出现「删掉一支照绿」。

### 3.3 `src` 是文件还是目录，契约表达不了

ccloop 契约是 `targetPaths: z.array(z.string())`，**没有 snakemake 那样的 `directory()` 标注**
（snakemake 还会事后验：`not (f.is_directory ^ os.path.isdir(f))` 不符抛 `ImproperOutputException`）。

⇒ **一律当前缀看**：路径 `p` 认领 `p` 自身 ∪ `p/**`。
⇒ **代价：过度圈定 ⇒ 损失并行度，不损失正确性。写进 spec，不当没看见。**

**归一化规则**（ccloop 的 `matches` 只认三种形式，**没有通用 glob**，调研 §5 第 5 条）：

| 声明 | 归一化成 |
|---|---|
| `前缀/**` | 前缀 `前缀/` |
| `**` | **仓库根** |
| 其余 | 完整路径，并按上面当前缀看 |

⚠️ **`**` 这一档要单独点名**：一个任务的 allowlist 写 `**` ⇒ 它与所有任务相交 ⇒
**整图退化成全串行**。这是**正确**的行为，但必须在 `orca plan`（§9）里**显眼地打出来** ——
否则人会把「并行没生效」当成 bug 去查。

⚠️ 归一化时**保留原始声明字符串用于报错**，不许只留归一化结果
（否则 `src/a.ts` 会显示成认领了 `src/a.ts/**` 这个不存在的目录，诊断变怪）。

### 3.4 🔴 这是优化，不是保证

见 §0.2。三条推论**写死**：

1. 判据说「不相交」⇒ 并行 ⇒ **合并时仍然可能冲突**。§5 的主干必须接得住，**这是常态不是异常路径**。
2. 判据说「相交」⇒ 串行 ⇒ 只是少了一次进主干的机会，**没有正确性含义**。
3. **不允许任何一条代码路径以「判据说不会撞」为前提做简化**（例如「不相交所以跳过合并冲突检查」）。

⇒ **第 3 条必须有一条判据钉住**（§10.2 的 S3），不是靠注释。**它是最容易被实现者顺手优化掉的一条。**

### 3.5 `--serial` 开关

> **C 必须有一个 `--serial` 开关把并行整个关掉；关掉之后结果必须仍然正确。**

它同时是三样东西：调试手段、§0.2 的最强验证形式、以及一条可跑的判据（§10.2 的 S10）：

> 同一份 plan，`--serial` 跑一遍、并行跑一遍，**两边的工作分支都要过两边 `requiredChecks` 的并集**。
> ⚠️ 判的是**都过验证**，**不是字节一致** —— 顺序不同内容本来就可能不同（§2.4 隐式边无天然方向）。

## §4 执行模型

### 4.1 两条现测事实（它们决定了整节的形状）

调研 §5 第 1、2 条，观测时点 2026-09-02：

1. **ccloop 从不 commit，也从不 apply patch。** 一次 attempt 是
   `git worktree add --detach`（`workspace/worktreeManager.ts:25`）→ agent 改 → 采 `diff.patch` →
   `git worktree remove --force`（`:30`）。⇒ **跑完之后目标仓库一个字节都没变**，
   产物只剩 `attempts/<n>/diff.patch` 这一份**文本**。
   ⇒ A′ §5.1 写的「上游向下游的交接物是一个 commit，不是一份文档」——
   **按 ccloop 今天的行为它就是一份文档。那是对 C 的期望，不是已成立的事实。**
2. **契约里没有任何字段能指定「从哪个 commit 开工」**（`git worktree add --detach <path>` 不带 commit-ish，
   契约 schema 81 行 `.strict()` 也无 base-ref 字段）⇒ 基点恒等于 `context.repoPath` 的当前 HEAD。
   ⇒ **C 只能靠控制 `repoPath` 本身来定基点。这就是「每任务一个 clone」的全部理由。**

### 4.2 基点策略：工作分支 W 的滚动 HEAD

```
default branch (main) ──┐   ← run 开始时取一次
                        ▼
          工作分支 W:  ●───●───●───●
                       ↑   ↑   ↑   ↑
                     base  T1  T2  T3   ← 逐个落地，HEAD 滚动
```

| | 规则 |
|---|---|
| **W 的诞生** | `orca run` 开始时从 **default branch 的 HEAD** 开出 |
| **基点** | **W 的当前 HEAD**。同一层的并行任务共用「该层开始时的 W HEAD」 |
| **「历史的工作」** | 已经落在 W 上 ⇒ **天然被继承**，不需要额外 merge 步骤 |
| **落地** | 逐个合进 W（§4.3）。先落地的推动 HEAD，后落地的**撞冲突就进 §5 主干** |

**五条当场拒 —— 但它们不在同一层，自查时不要合并计数**：
**前两条是 plan 层的**（§2.3 的六条里已含），**后三条是运行时前置**（读 plan 时还判不出来，第五条见 §4.2.1）。

| 拒 | 理由 |
|---|---|
| 🔴 **`W == default branch`** | 否则 C 就是在往 main 上合 —— 那是 **Tier 0，机制上禁止**。**这是 A′ §5.2 分档能成立的承重前提，必须是判据不是约定** |
| **W 已存在** | 自动复用 ＝ 在人不知情时往可能有别人工作的分支上合。⇒ W 的名字带内容 hash，重跑天然不撞 |
| **`policy ∉ {local-merge}`** | `rebase` / `pull-request` 配置认得但 v1 未实现 ⇒ **当场拒，不静默降级**（借鉴 6 反着借） |
| **基点不是一笔真提交** | `clone --local` 只克隆已提交状态 |
| 🔴 **目标仓工作树不干净** | C 会 checkout 主仓工作树，见 §4.2.1 |

#### 4.2.1 🔴 C 会 checkout 目标仓的工作树 —— 这是本设计唯一碰人的现场的地方

§4.3 第 6 步的 `git merge` 要求**主仓当前在 W 上** ⇒ *** **C 会 `git checkout` 目标仓库的工作树。** ***
**这不是副作用，是主路径。** §1.2 第 3 条那把锁挡的是**另一个 orca**，**挡不住人自己开着这个仓库在干活**。

⇒ **两条一起写死**：

1. *** **开跑前工作树必须干净（`git status --porcelain` 空输出），否则当场拒 exit 1。** ***
   口径**不许用 `git diff | wc -c`** —— 它对未跟踪文件完全看不见（§9.2 同款理由）。
2. **spec 必须显式声明 C 会动工作树。** 一个「悄悄 checkout 了用户仓库」的调度器，
   即使每次都成功，也是把人的现场当成自己的暂存区。

⚠️ **登记一条更干净但 v1 不做的替代**：把 W 的全部合并也放进 C 自己的一个专用副本里做，
最后只用 `git fetch` 把 ref 推回主仓 ⇒ **主仓工作树全程零触碰**。
**它更对，但要多一套 ref 同步机制**；v1 用「干净才让跑」这条当场拒换掉它，**代价写在这里，不藏。**

⚠️ **v1 的一处诚实限制**：W 只在 run 开始时从 default HEAD 取**一次**，之后不再追。
跑几小时期间别人推了 main，本轮吃不到。**「每层重取」是纯增量改动、不改任何判据语义**，登记为 v1 之外。

### 4.3 一个任务的六步

| 步 | 动作 |
|---|---|
| 1 | 基点 ＝ 本层开始时的 W HEAD |
| 2 | `git clone --local <targetRepo> <wd>/<run-id>/repo` ＋ `checkout --detach <基点>` |
| 3 | spawn ccloop（契约的 `context.repoPath` 改写成副本），**读 `loop-state.json` 的 `status`**，不只看退出码 |
| 4 | 收产物 —— 见 §4.4 |
| 5 | 结果 commit（由 §4.4 给出） |
| 6 | `git fetch <副本> <sha>:refs/orca/<run-id>` → `git merge --no-ff refs/orca/<run-id>` 落进 W。冲突 ⇒ §5 |

**逐个落地，不批量**（借鉴 11，bors-ng `divider.ex`）：**归因免费，不需要二分**。
代价是汇流串行化，**但汇流是秒级、跑任务是分钟到小时级**——该串的地方串对了。
**落地顺序本身是一次 `scheduling` 决策** ⇒ 进台账。

⚠️ **第 3 步「C 改写契约的 `repoPath`」不是一次 Tier 1 决策**：它没有 alternatives，是 C 的执行机制本身；
按 A′ §3.5，`alternatives` 为空 ⇒ **它压根不是决策**，落 Tier 2。**此处写明，免得读的人以为漏了。**

### 4.4 🔴 第 4 步：ccloop 必须先能交出 commit（**v1 的硬前置**）

#### 现测：`scripted` adapter 不产 `diffPatch`

**观测时点 2026-09-03，ccloop HEAD `0f7fc28e8bdc573ba22840d3c7e00e25d8927b17`：**

- `diffPatch` 是 adapter execute 结果的**可选**字段（`src/runtime/types.ts:42`），
  落盘处有守卫（`src/persistence/fileStore.ts:1738`：`if (artifacts.diffPatch !== undefined)`）；
- `/usr/bin/grep -n "diffPatch|changedFiles|artifacts" src/runtime/scriptedAdapter.ts` ⇒ **零命中**。

⇒ **v1 全程用 scripted ⇒ `attempts/<n>/diff.patch` 压根不会被写出来。**
⇒ **「v1 先用 patch 兜底、ccloop 那轮另开」这条路不成立。**

#### 现测：patch 这条路本身也是坏的

口径 `sed -n '190,260p' scripts/claude-phase-runner.mjs` 整份读回。`readDiffPatch`（`:232`）：

```js
readGitDiff(["diff", "--no-ext-diff", "HEAD"], worktreePath),                      // 已跟踪
readGitDiff(["diff", "--no-ext-diff", "--no-index", "--", "/dev/null", path], …)   // 逐个未跟踪
```

**未跟踪文件是被收进来的**（逐个合成 `/dev/null` diff）—— 这点 ccloop 做对了。但是：

| # | 坑 | 后果 |
|---|---|---|
| 1 | **两处都没有 `--binary`** | 二进制改动落成 `Binary files a/x and b/x differ` —— **`git apply` 应用不了** |
| 2 | `maxBuffer: 10 * 1024 * 1024` | 超 10MB 的 diff 抛错，而 `readGitDiff` 的 catch **只对 `code === 1` 返回 stdout，其余一律返回 `""`** ⇒ **补丁被静默吞成空** |
| 3 | 同一个 catch 吞掉任何其它 git 失败 | 也是空 |

#### 结论：ccloop 的改动是 v1 的硬前置，且是纯追加

**要改的（满足 ccloop 铁律 2「能不能只加不改」）**：

1. attempt worktree 里 agent 跑完后：`git add -A` → `git commit`；
2. **在 `git worktree remove --force` 之前写一个 ref** —— `refs/ccloop/<run-id>/attempts/<n>`。
   worktree 与 `repoPath` 共用同一个对象库 ⇒ **commit 对象本来就在那儿了，缺的只是可达性**。
   不写 ref 它就等着被 GC。**这一步是整个改动的全部机关。**
3. 把 sha 报进 `attempts/<n>/` 的产物里；
4. **`diff.patch` 原样保留**（继续当人读的证据）。

⇒ 它**与 adapter 无关**（commit 在 worktree 里做）⇒ **一处改动同时管 `scripted` 和 `claude` 两条路。**

⚠️ **这是对 ccloop 的改动，要在 ccloop 自己的仓库里走它自己的流程**
（它有一轮在飞的工作：E1 的 I-2 ＋ 人裁 85）。人已授权 Orca 这条线可以改它，
但**改之前先报「要改什么、为什么非改不可」**，且守它自己的铁律，**push 仍需人单独点头**。

### 4.5 其余规则

- **main／push ＝ Tier 0，C 代码里没有任何一条路径 checkout default 分支或跑 push**。
  **判据是行为不是文本扫描**：整轮跑完断言 default branch ref **前后 sha 一字未动**（§10.2 的 S14）。
  文本扫描（「源码里不许出现 `push`」）太脆：注释、字符串、变量名都会误伤，**而且扫得过不等于跑起来不碰**。
- **W 不删**（删分支需人授权，Rule 15），跑完打印名字与 tip。
- **任务副本目录：成功的删，失败的留** ＋ 打印路径；`--keep-workdirs` 全留。
- **删一律 `/bin/rm -rf`** —— 本机 `rm` 有 `-i` alias，普通 `rm -rf` 会**静默挂在确认提示上直到超时**。
- **`clone --local` 的代价**：走硬链接，**对象库不复制**，但**工作树是真文件**。
  ⇒ 这条定了 `--keep-workdirs` 的默认值：**默认不留**。
- ⚠️ **「N 个并行 worktree 会争 `.git` 的 worktree 列表锁」这条论断是推理，未实测。**
  它**不需要实测** —— clone 方案独立成立，不依赖它为真。**不许把未实测的推断写成实测事实。**

## §5 冲突处理主干

### 5.0 它是主干，不是异常路径

见 §0.1 第 1 行、§0.2。**必须能在判据完全失效时仍然收敛** ——
极端情况：全部任务都声明成互不相交、实际全撞。**那种输入下 C 必须仍然给出正确结果，只是慢。**

### 5.1 四步分工

| 谁 | 干什么 | 依据 |
|---|---|---|
| **代码** | 检测（`git merge` 退出码）、枚举冲突块、定合并次序 | Rule 5：代码能答就代码答 |
| **模型** | 逐块**分类**（文本型／语义型），并解掉文本型 | Rule 5 明列 `classification` 该用模型 |
| **代码** | **验证**：跑两边契约 `verification.requiredChecks` 的**并集** | 不过验证就不算解决 |
| **人** | 只处理**语义型残余** | Rule 7：势均力敌才升人 |

**分档依据**（A′ 未写，本文补）：

- **文本型**：两边各加一条 import、改了相邻行、格式冲突 —— **证据能分胜负 ⇒ agent 自己判**。
- **语义型**：两边对同一段逻辑做了不相容的**有意选择** —— **势均力敌 ⇒ 升人**。

> **分类可能错，而这不承重**：分类错成「文本型」并解错了 ⇒ **验证不过 ⇒ 退回升人**。
> **分类错不会静默通过。这是本节最重要的结构性质。**

### 5.2 唯一保留的硬约束：解冲突的不能是当事任务（借鉴 4）

当事方缺对方的意图，会**可靠地**要么覆盖对方、要么放弃自己
（hermes `kanban.md:954` ＋ 它的 `merge-reconciler` skill）。

**机制怎么保证？** 直接给 ccloop 跑一个和解任务**行不通**：
ccloop 的 `git worktree add --detach` 会开一个干净 worktree，而
**冲突状态活在 index 里，不在任何一笔 commit 里** —— agent 根本看不见。

⇒ **办法：把冲突物化成一笔提交。**

```
1. C 在副本里 git merge → 冲突
2. git add -A + commit  → 一笔「冲突态」提交（工作区里带 <<<<<<< 标记，是纯文本）
3. spawn ccloop，基点 = 那笔冲突态提交，goal = 消除冲突标记
   → agent 在 worktree 里看得见冲突标记
4. 拿和解后的树，用 git commit-tree 重构一笔【正确的】merge commit
   parent = [W 的前 tip, refs/orca/<run-id>]，tree = 和解后的树
5. 冲突态那笔提交留在副本的临时 ref 上，永不进 W
```

⇒ W 上看到的是一笔**正常的 merge commit，两个 parent 正确**，归因干净。
且和解全程复用 ccloop 管线（验证、租约、证据采集），**C 不需要自己的模型 adapter**。

⚠️ **和解契约由 C 合成**（原 spec 漏写了这件事，自查补上）：它不是人写的，
C 把两边契约的 `goal` / `successCriteria` 拼进一份新契约，**写进 `runsDir`** ——
**因此它天然满足 §2.3「契约文件必须落在 `targetRepo` 之外」那条当场拒**，不需要例外。

⚠️ **「不是当事任务」的成立性来自上下文构造，不是进程边界**（同一个模型、可能同一份上下文）。
⇒ **变成一条机械检查**：和解契约的 goal 里**必须同时引用两个 taskId 的 goal 与 successCriteria**，
否则**拒绝派和解、直接升人**（exit 3）。
**当事任务的契约里只有自己那一边 —— 这条检查正是在量这个差别。**
⇒ 场景 **S20**，变异 **`M-RECON`**。

⚠️ **§5.2 第 4 步是本节最脆的实现点**（手工构造 git 历史）⇒ **判据直接量结果，不量过程**：
> 和解后那笔 merge commit 的两个 parent **恰好**是 `W 前 tip` 与 `refs/orca/<run-id>`；
> 且 `git rev-parse <c>^{tree}` 与和解后副本的树 **逐字节相同**。

⚠️ **和解失败时副本必须留**（§4.5 已有「失败的留」），escalation 文件里写明副本路径与临时 ref 名 ——
**冲突态那笔提交是和解过程的唯一现场**。成功时删掉是对的。

### 5.3 🔴 验证并集为空 ⇒ 直接升人

两边的 `requiredChecks` 都空 ⇒ 并集是空 ⇒ **任何和解都"通过"** ⇒
**又是一次「绿是空的」，而且是自动产生的。**

> **`requiredChecks` 并集为空 ⇒ 当场拒绝自动和解，直接升人。**

配点名变异：删掉它 ⇒ 喂两个无 checks 的任务 ⇒ 和解"成功"通过 ⇒ **判据必须红**。

### 5.4 升人的形式

调度器**停在那个合并点**：

1. 把**两边意图 ＋ 冲突块 ＋ 可执行的 `undo.how`** 写进 `<runsDir>/escalations/<run-id>.md`
   （**不写进 W** —— W 是代码分支，不该塞流程文件）；
2. **非 0 退出**（exit 3，§6.3）；
3. 打印副本目录的路径（人在那儿手工解）。

⚠️ **v1 的升人是终止性的：不做增量 resume。** 人处理完**重跑整个 plan**
（内容导出的 id 会撞 ⇒ 递增 ⇒ 新 run）。
⇒ **代价：已跑完的任务白跑。** v1 是 scripted、不花钱，无所谓；**真跑很贵**
⇒ **登记为 v1 之外的头号候选**（§10.4 缺口 4）。

⚠️ **这条不能靠 ccloop 的 `resume` 化解** —— §6.4 现测：`blocked_waiting_human` **不可 resume**。

### 5.5 每块判断进台账 —— 顺带发现 A′ 白名单的一个缺口

和解时逐块做的每个判断都是 agent 替人做的选择 ⇒ **Tier 1**，
`undo.how` 天然写得出（`git branch -f W <ref>`），**自动过 A′ 闸门 A**。

**但 `kind` 填什么？** A′ §3.6 白名单是
`dependency` / `interface` / `scheduling` / `abandon` / `criteria` / `boundary` ——
**没有一个装得下「和解」**。

⇒ **新增 `reconcile`**。理由：混进 `scheduling` 会让面板分不清「排序选择」和「代码内容选择」，
**而后者风险高一个量级**。

⚠️ **代价如实登记**：要改校验器代码 ＋ 加判据 ＋ 点名变异，而 handoff 已警告
**`validateLine.ts` 里有第四份引用事件清单，加第五种类型时会咬人**。
⇒ **实施时第一步是做一次「白名单／清单在代码里有几份副本」的普查**，
**普查清单从被改的那句话机械导出**（ccloop 历轮教训：第一轮改 12 漏 6，第二轮补 6 又漏 2，**半改比不改坏**）。
**不许直接加。**

## §6 状态与路由

### 6.0 现测：退出码把四个终态压成同一个 2

**观测时点 2026-09-03，ccloop HEAD `0f7fc28e8bdc573ba22840d3c7e00e25d8927b17`**：

`src/cli.ts` 末尾，`run` 与 `resume` **两处一模一样**：

```js
return finalState.status === "succeeded" ? 0 : 2;   // catch 里 return 1
```

⇒ **C 必须读 `<runDir>/loop-state.json` 的 `status`**（§1.2 的具名更正）。

`src/state/types.ts:3` 的 `RunStatus` 九档；`src/state/stateMachine.ts:3` 的 `legalTransitions` 里
**空数组 ＝ 终态**（`isTerminalRunStatus` 就是从这张表导出的，**不是另抄一份** —— 这点它做得好）：

```
queued planning executing verifying                            ← 非终态
succeeded blocked_waiting_human exhausted cancelled failed     ← 五个终态，全是 []
```

⇒ **`blocked_waiting_human: []` —— 在 ccloop 里「等人」是终态。**
调研借鉴 2 写的「等人不是终态」是**从 Airflow 借来的应然，不是 ccloop 的实然。**

### 6.1 四个非成功终态各自路由（借鉴 2）

| ccloop 终态 | C 的路由 | 后代 |
|---|---|---|
| `succeeded` | 进 §7 事后核对 → 落地 | 正常继续 |
| `blocked_waiting_human` | **升人，但这个任务不算失败** | `upstream_not_run`；**其余分支继续** |
| `exhausted` | 失败（预算／尝试用尽） | `upstream_not_run` |
| `failed` | 失败 | `upstream_not_run` |
| `cancelled` | **整轮停** —— 人按了停，让别的任务接着跑是违背意图 | 全部 `upstream_not_run` |

⚠️ **「整轮停」有歧义，钉死**：**不再启动新任务；已经在跑的【不额外杀】，等它们自己结束。**
理由：停止信号是打给**进程组**的，同层的兄弟任务本来就会各自收到并落到 `cancelled`；
C 再去杀一遍是重复且会与 ccloop 的租约／owner-transfer 抢时序。
⇒ **C 在这里做的是「不再发新的」，不是「把在跑的掐掉」。**

⇒ **撤回**先前那条粗判「非 succeeded ⇒ 后代全 blocked」：**四个终态给人的信息完全不同，压成一个就把信息扔了。**

### 6.2 C 自己的两个终态

| 终态 | 含义 | 依据 |
|---|---|---|
| **`upstream_not_run`** | 前驱没跑成，本任务**从未开工** | 借鉴 10：Airflow 的 `UPSTREAM_FAILED` 与 `FAILED` **并列且都是终态**。「它没跑过」和「它跑坏了」读台账时天差地别 |
| **`succeeded_but_empty`** | ccloop 报 `succeeded`，而**产物树与基点一字不差** | §4.4 的三条静默转空通道；借鉴 9：snakemake 逐字的 *completed successfully, but some output files are missing* |

**这两个是「图这一层」的事实，ccloop 根本不知道有图** —— **不是在重造它的状态机**
（Airflow 也正是这么分层的：`UPSTREAM_FAILED` 是调度器的状态，不是 task 自己的）。

### 6.3 整轮退出码

借鉴 14 是**反面教材**：nextflow 的 `IGNORE` 策略下默认 exit 0，
要 `workflow.failOnIgnore: true` 才非 0。

> **C 绝不能有「有任务失败但整轮 exit 0」的档位。没有 `--ignore-failures`，一个都不给。**

| 码 | 含义 |
|---|---|
| **0** | 全部任务 `succeeded` **且**全部落地 |
| **1** | 用法错／输入被拒（§2.3 的六条 ＋ §4.2 的三条运行时前置，合计九条，重叠两条）|
| **2** | 有任务落在非成功终态，或有 `succeeded_but_empty`，或 §7.3 方向一第二档 |
| **3** | **升人**（语义型冲突残余、§5.3 并集为空、§7.3 方向一第一档、**§6.1 的 `blocked_waiting_human`**、§5.2 的和解契约被拒） |

🔴 **优先级必须写死，否则「同时有失败又有升人」时退出码是未定义的**：

> *** **3 > 2 > 1 > 0。只要发生过任何一次升人，整轮就是 3，哪怕另有任务失败。** ***

理由：**2 是「这条路断了，读日志就够」，3 是「有人必须回来做一件事」。**
把 3 降级成 2 会让那件必须做的事消失在一堆失败里；反过来只是多提醒一次。
⚠️ 这条同时补上一处遗漏：`blocked_waiting_human` 在 §6.1 里明写「升人但不算失败」，
**而先前的退出码表里它既不在 2 也不在 3** —— 那是本 spec 自查抓到的一处真空。

⚠️ **诚实登记**：handoff 已记过「退出码 2 目前没有任何消费者 —— `set -e` 与 `&&` 把 1 和 2 一样地当停」。
**3 同理。** ⇒ 这套分档是给**读日志的人**和**未来的面板**用的，**不是给 shell 用的**。
**判据不许写成「shell 会区别对待」。**

### 6.4 现测：`blocked_waiting_human` 不可 resume

`src/controller/resumeLoop.ts:98`：

```ts
const RESUMABLE_STATUSES: readonly RunStatus[] = ["planning", "executing", "verifying"];
```

不在其中就返回 `run status <s> is not resumable`（`:124`）。

⇒ **「等人」在 ccloop 里不只是终态，而且不可恢复。**
⇒ **C 这层的「暂停等人」只能由 C 自己实现（重跑），不能靠 ccloop 的 resume。** §5.4 已按此写。

### 6.5 `succeeded_but_empty` 的一处已知代价

**一个任务【合法地】什么都不改**（例如 goal 是「确认 X 已经是对的」）会被判成失败。

**v1 的答案：一律当失败。** 理由：本仓库历史里「空的绿」是更常见、更贵的坏法。
如果任务确实合法为空，**那应该由契约显式声明**，而那个字段今天不存在
⇒ **登记为对 ccloop 契约的第二条建议**（§10.5）。**是建议，由 ccloop 自己决定。**

## §7 事后核对（双向）

### 7.0 它在我们这儿比在别的系统里高一档（借鉴 16）

pants 靠**读 import 推断** `dependencies` ⇒ 它能在**构建时**发现漂移。
**我们没有推断可用** —— 不可能在 agent 跑之前知道它将写什么。

⇒ **事后核对是 C 唯一的漂移检测手段，而且我们只能在【付完钱之后】才发现。**

### 7.1 两个方向，都要

| 方向 | 含义 | 性质 |
|---|---|---|
| **实际 ⊄ 声明** | 写到声明之外 ⇒ 本层的并行判定**可能已经失效** | 安全方向 |
| **声明 ⊄ 实际** | 声明了却没产出 ⇒ **这任务可能什么也没干，而退出码说它成功了** | **「绿是空的」** |

A′ §5.1 只写了方向一。**方向二在本仓库历史里是更常见的坏法。**

### 7.2 数据源：C 自己量，不消费 ccloop 的 `changedFiles`

ccloop 采的是 `git status --porcelain=v1 -z --untracked-files=all`
（`scripts/claude-phase-runner.mjs:198`；`runLoop.ts:505` 的 `observeChangedPathsBestEffort` 同理）
——**不是模型自报**，这点它做对了。但入口叫 **best effort**。

⇒ **C 不用它。C 自己量**：副本里 `git diff --name-only <基点> <结果 commit>`。
理由：**不 best-effort（失败就是失败，fail loud）**、**不依赖 ccloop 的实现细节**、
**两笔 commit 之间的 diff 是确定性的**。

⚠️ **代价写明**：C 量的是**净改动**，ccloop 量的是**过程中碰过的文件**。
一个文件被改了又改回去，ccloop 报它、C 不报。

> **划界：C 的核对服务于【并行正确性】，不是【安全审计】。**
> 安全审计是 ccloop `evaluatePathPolicy` 的事（而它是纯事后检测器）。
> **两个目的用两个数据源，不要混成一个。**

### 7.3 核对不过怎么办

#### 方向一（写到声明之外）：分两档，机械可判

钱已经花了，**不能回滚"没写"**。但可以决定它进不进 W：

| 越界路径 | 处置 | 退出码 |
|---|---|---|
| **与本层其它任务的写集相交**（复用 §3.2 的字典树） | **拒绝落地 ＋ 升人** —— 并行判定已经失效，两个任务可能已互相破坏 | 3 |
| | ⚠️ **为什么是「本层」而不是「全图」**：只有**同层并行**的任务才是从同一个 W HEAD 各自开工、互相看不见的。**后续层的任务从「已含本任务落地结果」的 W 开工 ⇒ 它继承而非并发** —— 那里的越界只会变成一次普通的合并冲突（§5 接得住），**不是静默互坏**。 | |
| **与其它任务都不相交** | **照落地**，记台账（Tier 1，`kind: boundary`） | 2 |

⇒ 这个分档正是 §0.2 的兑现：**声明写窄很常见且多数无害，一律丢掉是巨大浪费；
但一旦它和别人撞上，就不是浪费问题了。**

#### 方向二（声明了却没产出）：全空失败，部分放行

| | 处置 |
|---|---|
| **净改动全空** | `succeeded_but_empty` ⇒ **失败**（exit 2） |
| **部分未产出**（声明 3 个，改了 2 个） | 记台账 ＋ 警告，**不失败** |

⚠️ **snakemake 在这里是一律失败的**（`MissingOutputException`）。**我们放宽必须给出理由**：

> snakemake 的 output 是**规则声明的产物**（精确、机器生成）；
> 我们的 `targetPaths` 是**人写的意图范围**（粗、通常写宽）。
> 拿精确契约的严格度去要求粗糙契约，只会训练出「把 `targetPaths` 写到最小」的反向激励 ——
> **而那恰好是 §3.1 里不安全的那个方向。**

### 7.4 核对本身必须被看见打红

见 §10.3 的 `M-A1` / `M-A2` / `M-B1` / `M-C`。
其中 **`M-C`（把整个核对跳过，看判据是否仍绿）抓的不是某条分支，是整节的存在性** ——
这是「**同一个不变量查两遍**」（snakemake 在 `dag.py:1276` 查一次、`check_jobs` 里穷举再查一次，
注释写明第一道有覆盖洞）。

### 7.5 一处已知缺口

**整个 §7 建立在「C 拿得到基点和结果两笔真 commit」上。**
在没有 §4.4 那条 ccloop 改动之前，**方向二退化成「patch 空不空」——
它分不清「ccloop 采集失败」和「agent 真的没干活」。**

⇒ 这是 §4.4 那条改动的**第三个理由**，也是**最硬的一个**：它坏的是核对本身。

## §8 台账接线

### 8.0 台账住目标仓库 —— 但目标仓库有 N 个副本

A′ §9.2：`.decisions/` **既不住 Orca 也不住 ccmem，住在被干活的那个目标仓库里**。
**Orca 装的是工具，不是台账。**

⇒ 每任务一个 clone，副本有 N 份 ⇒ **分两类**：

| 决策的作者 | 写哪 | 怎么进版本库 |
|---|---|---|
| **任务内的**（agent 跑任务时做的） | **该任务副本**的 `.decisions/<run-id>.jsonl` | 随该任务的 commit 落进 W |
| **C 自己的**（排序、和解、越界处置） | **主仓 W** 上的 `.decisions/<orca-run-id>.jsonl` | C 在 W 上单独提交 |

⚠️ **两类文件名不同 ⇒ A′ §3.1「结构上不可能冲突」在这里仍然成立**，不需要新机制。

### 8.1 C 会写哪些决策

| 时机 | `kind` |
|---|---|
| 隐式边定向（相交但无天然先后，§2.4） | `scheduling` |
| 落地顺序（§4.3） | `scheduling` |
| 冲突逐块和解（§5） | **`reconcile`**（新增，§5.5） |
| 越界但不相交 ⇒ 照落地（§7.3） | `boundary` |
| ccloop 调用方式：npm 依赖 → spawn（§1.4） | `dependency` |

### 8.2 必须走 `appendEvent`，而且写入方要补两条检查

C **不许手写 JSONL** —— 写入方是 fail-closed 的（`src/ledger/writer.ts`：校验后才写，
`rejected` 与 `downgraded` 都抛），手写等于绕开六项检查。

但 handoff 登记过写入方的两个缺口，**它们在 C 这里第一次真的会咬人**（C 同时写多个文件、多个 run）：

1. `appendEvent` **不校验事件的 `run` 字段与文件名是否一致**；
2. **不拒绝重复的 decision id**。

**在写入方里补，不在 C 里加一层。** 理由是 A′ §3.8 自己那句话：

> 「一条记录合不合法**不能靠写它的 agent 自觉**」

⇒ **在 C 里加一层，就是让第二个消费者（B／D／E）重犯同样的错。检查属于唯一的写入口。**

⚠️ **代价如实登记**：改已发布代码 ＋ 两条新判据 ＋ 两条点名变异。
**与 §5.5 的 `reconcile` 是同一处改动（都在 `src/ledger/`），合成一个实施任务，且必须排在最前面** ——
因为之后每一条决策都要经过写入方。

### 8.3 🔴 `bound` 行必须先写进树，再 `commit-tree`

A′ §3.3：`decision` 在决策时写，**`bound` 那一行落在实现那笔提交里**，
「哪笔实现了它」由 `git blame` 反查 `bound` 行得出。

⇒ 在 C 这儿有一个**极易踩反的时序**：和解后的 merge commit 是 `commit-tree` 构造的，
**树在构造那一刻就定死了**。

> **实现顺序必须是：先把 `bound` 行写进 `.decisions/`，再 `commit-tree`。**

实现者会非常自然地写成「先 merge，再记账」—— 那样 `bound` 落在**下一笔**上，
`git blame` 反查到**错的提交**，而且**一切照绿**。
⇒ 配点名变异：把两步调换 ⇒ 断言 `bound` 行的 blame 恰好是那笔 merge commit ⇒ **必须红**。

### 8.4 squash 不可禁止，只能有准备

**C 自己不提供 `squash-merge` 档位** —— 但那只管得住 C。
**人在 GitHub 上点 Squash and merge 是 C 完全够不着的动作**（§0.1 第 3 行）。

**squash 到底毁掉什么（先说清，别夸大）**：它**保留最终树** ⇒
**`.decisions/` 的行内容一个字都不丢**。毁掉的只有**归属**：
`git blame` 会把所有 `bound` 行归到那一笔 squash commit。
⇒ **受损的是索引器（E）反查的精度，不是台账本身的有效性。**

**三条准备**：

| | 动作 |
|---|---|
| ① **检测**（启发式，可算） | 一笔提交若新增了**属于 ≥2 个不同 run-id 的 `bound` 行**，它极可能是 squash 的产物 —— 正常的逐个落地一笔只引入一个任务的行。**不是证明，但可报** |
| ② 🔴 **`bound` 事件里加 `taskId` ＋ `runId` 字段** | **用一个 git 历史改写毁不掉的标识，替换掉一个会被毁掉的代理。**「哪个任务实现了它」通常才是人真正要问的；「哪笔提交」只是它的代理 |
| ③ **索引器降级** | 检测到 ⇒ 把这些 `bound` 的 commit 归属标成 `ambiguous`，**而不是记一个错的 commit**。**「不知道」比「知道错的」好** |

⚠️ **② 必须现在做，不能等到实现 PR 档位的时候。**
**台账只追加** —— 格式定下来之后，已经写下的行**永远补不上这两个字段**。
①③ 是消费侧，日后随时能加；**② 是写入侧，错过就错过了。**

**policy 表的三种「没有」要分开写**：

| policy | 状态 |
|---|---|
| `local-merge` | v1 唯一实现 |
| `rebase` | 配置认得，v1 未实现 ⇒ 当场拒。**A′ §3.2 说 rebase 的归属是准的，所以它日后可以有** |
| `pull-request` | 同上，且天然 Tier 0（对外）。**它一旦实现，squash 就会从外部进来 —— ②③ 就是为这一天准备的** |
| `squash-merge` | **C 不提供这个档位**（≠「禁止 squash 发生」） |

### 8.5 `ledgerMode`：目标仓库可能不想要 `.decisions/`

| 值 | 含义 |
|---|---|
| `in-repo`（默认） | A′ §9.2 原样 |
| `out-of-repo` | 写进 `runsDir`，**用绝对路径 ＋ 内容 hash 代替 commit 锚点** |

⚠️ 后者**不是新造的档**，就是 A′ §3.7 那条「非 git 目录」，
而 **A′ 已经明说它弱**：没有不可变锚点，历史可被就地改写而无从发现。
**连同它自陈的弱点一起继承。**

### 8.6 记账提交会污染 W 的历史

**v1 接受。** W 是工作分支不是 main，历史干净度不是首要目标。
⚠️ **但要堵死那个诱人的"优化"**：把记账提交攒起来 squash 掉 —— 见 §8.4。

## §9 `orca plan` —— 花钱之前先让人看见图

### 9.1 它打印什么（借鉴 15，pants `pants dependencies <target>`）

| # | 内容 |
|---|---|
| 1 | 每个任务的**写集**：归一化后的 ＋ **原始声明字符串**（§3.3） |
| 2 | **全部相交对**，逐对列出冲突路径并标明是 §3.2 三种冲突的**哪一种** |
| 3 | **DAG 分层** ＋ **每层并行度** |
| 4 | **落地方式、W 的名字**，以及【九条】当场拒的检查结果 —— §2.3 的六条 ＋ §4.2 的运行时前置（W 已存在、工作树不干净都读得出来，读 ref 与 porcelain 不算「碰」） |
| 5 | 🔴 **退化警告**：某任务写集归一化成仓库根（`**`）⇒ **它与所有人相交 ⇒ 整图串行**；并行度恒为 1 ⇒ 明说「这份 plan 没有任何并行」 |
| 6 | 🔴 **`requiredChecks` 并集为空的相交对** ⇒ 预警：这对一旦冲突会**直接升人**（§5.3），不会被自动和解 |

第 5、6 条是**主动预警**，对应「跑起来才发现白等一场」的两种最贵形状。

### 9.2 零副作用，而且要有判据

`plan` **不建分支、不 clone、不 spawn、不写台账、不碰目标仓库一个字节。**

**判据**：跑前跑后，`targetRepo` 的**全部 ref 的 sha** 与 `git status --porcelain` 输出**逐字节相同**。

⚠️ **不许用 `git diff | wc -c` 做这个证明** —— handoff 实测：
**`git diff` 对未跟踪文件的内容改动完全看不见**，覆写一个未跟踪文件前后都是 0 字节。
**要量什么就直接量什么。**

### 9.3 退出码：0 合法 / 1 被拒，**警告不影响退出码**

借鉴 14（绝不能有「有问题但 exit 0」）在这里**不适用**，区分写清：

> `plan` 回答的是「**这份 plan 合不合法、它会怎么跑**」。**退化（全串行）不是不合法** —— 人可能就是想全串行。
> `run` 回答的是「**跑完了没有、有没有任务坏掉**」，**那里一个 exit 0 的例外都不给**。

### 9.4 `plan` 与 `run` 必须是同一份代码

两份实现**必然漂移**，而漂移的方向恰好最坏：**人看到的图和实际跑的图不是一个**。

⇒ **两条一起做**：

1. `plan` 就是 `run` 的前半段（读 → 校验 → 算写集 → 建图 → 分层）**在执行前停下并打印**，**同一个函数**；
2. **`run` 开头【总是】打印 plan 的那份输出。**

⇒ 这样它们**不可能漂移** —— 不是靠判据保证，是**结构上只有一份**。

### 9.5 两条输出纪律

- **相交对是 N² 量级**：默认打摘要 ＋ 总数，`--verbose` 打每对全部冲突路径。
  ⚠️ **绝不许截断成 `[+N more]`** —— handoff 记过 rtk 的这种骗法。**截断是最坏的第三种。**
- 🔴 **输出里必须写死一句**：
  > 这些是**声明**的写集。实际写集只有跑完才知道。**不相交不保证不冲突。**

  ⚠️ **这句话不能当脚注放末尾，要和「每层并行度」打印在一起** —— 那才是人据此做决定的地方。
  **放错位置的警告等于没写。**

## §10 成功判据与已知缺口

### 10.1 判据是一条能跑出 0／非 0 的命令（Rule 4）

```
npm run verify:scheduler      # 建一次性沙盒仓 → 跑全部场景 → exit 0 或非 0
```

**散文判据没法循环到「验证为止」**，因为没有任何一刻能判定它成立了。

🔴 **它必须被接进 `npm run verify`**（本仓库现有的那条闸门），**不许只当一个独立脚本**。
理由是本仓库自己的实测教训：*** **`core.hooksPath` 那道门曾经以未武装状态出厂** *** ——
一个没人跑的判据和一个不存在的判据，**在 CI 输出里长得一模一样**。
⚠️ **代价如实登记**：`verify` 会因此变慢（要建沙盒仓、跑多轮 orca）。
若慢到影响 pre-commit，**正确的处理是给它分档（`verify` vs `verify:fast`）并说明哪一档在门上，
不是把它从 `verify` 里拿掉。**

### 10.3 点名变异表

**每新增一个分支，点名那条删掉【它自己】的变异，并确认它存在且被看见红**（§0.3）。

🔴 **每条变异必须点名【喂它的那个场景】。** 没有具名场景的变异，正是 ccloop 栽过的
「**没跑过的那条变异**」—— 八条变异看着完备，某一支却只被别的分支的变异间接掠过，
**结果它删掉全套照绿**。

### 10.7 ⚠️ 本 spec 的范围自查结论：**它装不进一份实施计划**

本文的自查（占位符／内部一致／范围／歧义）在**范围**这一项上没有通过。诚实登记：

本文要求的东西横跨**两个仓库、三个可独立验收的块**：

| 块 | 内容 | 能不能单独验收 |
|---|---|---|
| **P0** | **ccloop 交出 commit sha**（§4.4） | 能。**在 ccloop 仓库、按它自己的流程**做，且是后两块的**硬前置** |
| **P1** | **A′ 台账的三处扩展**：`reconcile` kind、写入方两条检查、`bound` 的 `taskId`/`runId` 字段（§5.5 §8.2 §8.4②） | 能。**必须先做那次「白名单有几份副本」的普查** |
| **P2** | **C 本体**：§2–§9 ＋ §10.2 的 **22 个场景** ＋ §10.3 的 **14 条点名变异** | 能，但依赖 P0、P1 |

⇒ **接 `writing-plans` 时应当出三份计划（或一份含三个明确阶段的计划），不是一份平铺的。**
⇒ **P1 有一处不能延后**：§8.4② 的 `bound` 字段是**写入侧**的 ——
**台账只追加，格式错过就永远补不上**。它必须在 C 写下第一条 `bound` 之前落地。

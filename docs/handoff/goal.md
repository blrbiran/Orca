## 2. 设计原则（P1–P7；引用时引编号）

### P1 全局最优：深挖共性，普适、可扩展（人裁，2026-10-21，会话 `8b1469ea`）

> 你要从全局最优的角度考虑，而不仅考虑破坏性大不大。现在产品还未发布，还是做破坏性改动的最佳时期。

> 现在是破坏性大改的最好时候，你需要反复思考再思考（我不介意你花大量的时间去调研和思考，甚至可以多做几个session我都不介意），看如何做是全局最优的。要深挖共性的部分，同时需要降低人对整个流程的介入，思考如何尽量不等人、不靠人，但是人需要保留反驳、反悔、修改、提出新意见的权利，还要考虑普适性和可拓展性。

读法（控制器整理）：
- **判断方案看长期的普适性与可扩展性**，改动大小不是主要依据；发布前的破坏性改动可以接受，旧名字不留别名。
- **先找跨场景的共性，再做场景差异**：同一套引擎、少量由代码拥有的步骤种类，场景差异由数据（模板、prompt、skill 组合）表达，不另写一条流水线。
- 大设计先调研（读同类开源实现的源码）再提方案；方案要能说清「为什么这是共性」。

### P2 不等人、不靠人（人裁，2026-10-20，会话 `308b874c`；原 §1.4）

> 要，这就是我做 orca 的意义。提高效率不要被等人的相关操作block住。

> 其实我更希望orca能自动编排各个group 之间的顺序和串联、并联关系。通过kanban拖拽来启动 group 的逻辑应该弱化。

> 现在默认不限额。needs-human 这类状态如果挡住就尽量跑后续的group，不要被挡死。

同一方向的裁定：改弱的测试「可以先落地，不要block住，但是需要标红提醒人 review」；agent 版本升级「直接用新版本继续」「静默更新就行」。

读法：
- **确认就是开跑的授权**；前置完成就自动往下走。
- **一处等人只停住它自己和显式依赖它的部分**，其余照常跑。
- **先跑后审，标红而不是闸门**。真正要停下来等人的，只有「错了发现不了、或者没法便宜地重做」的动作（对外发送、发布、花钱、推送）。
- 顺序靠显式依赖＋落地时解决冲突，不靠事前猜写集。

### P3 人始终有权反驳、反悔、修改、提出新意见（人裁，2026-10-21，会话 `8b1469ea`；吸收原北极星的「掰得回来」）

> 人需要保留反驳、反悔、修改、提出新意见的权利

> 写意见和直接动手都要能接受（流程停在把关步骤时）

> 人通过 agent 做的动作，不也算人做的选择吗。所以我理解可以适当放宽。

读法：
- 人在任何时刻都能介入：写意见、直接改产出、撤回、纠正；介入后系统**按人的意见接着走**，不是从头再来。
- 人的修改与撤回都留痕、可追溯（谁担责 `by`、经什么途径 `via`）；人写的值优先于 agent 写的值。
- 不可逆动作（Tier 0：push、强制形式）与付费仍需人点头（CLAUDE.md Rule 15）。
- 人通过自己在场的 agent 做的动作算人的选择；Orca 自己派出去、无人值守的 run 不能替人做只限人的事（CLI v2 spec §15–§16）。

### P4 人少填，默认值可改（人裁，2026-10-18，会话 `a3b2a7a7`；原 §1.1）

> 我整体的思路是orca的整体操作要简单，agent 能帮人做的就尽量帮人做掉，尽量不要让人填东西。但是保留人修改默认值的能力。

读法：默认值由 Orca／agent 给，人不填也能走完；改默认值的入口始终保留，人填的为准；agent 写的标明是 agent 写的。管的是「填东西」，不管「授权」。

### P5 报给人的决定少而关键，分级，可追认（人裁，2026-10-20，会话 `3831d12f`；原 §1.3）

> 都怕。但是我更倾向于尽量少提供决定给人审，因为人的精力有限，但是这些决定都要很重要，orca这个系统就是要把人从AI coding 的必要流程里摘出来，但是人必须要能时候追认关键改动，做关键决策。

> 这些也可以算决定。其实决定可以分级。可以默认只显示高优先级或者说重要的决定。其他次要的决定如果人愿意看可以有机会看、有机会改就行。

读法：决定分级（major／minor），默认只显示重要的；headless 下 agent 自己选、继续做，报决定是给人事后看；每条在 Web UI 可见、可纠正（纠正 ⇒ debug task）。

### P6 每个动作都能在 Web UI 和 agent 通路里走完（人裁，2026-10-18，会话 `a3b2a7a7`；原 §1.2；2026-10-21 补）

> 所有动作都需要在 web UI 中可以完成，orca 的 agent 通路也要全流程可以走完，不能依赖人手动在命令行操作。

> （2026-10-21）需要尽量优化，防止大量占用其他 agent 的上下文 … 主推 cli + skill 的方式，并且尽量精简 MCP 对上下文的占用

读法：每个能力都有 Web UI 入口；agent 通路能把同一条流程从头走到尾，**主推 CLI＋skill**，MCP 只留一个极小的工具；完成判据要点名 UI 与 agent 通路各自怎么走完。

### P7 代码判，模型判断；成本只报工具给出的数（CLAUDE.md Rule 5、Rule 14；原 §1、§6）

- 调度、依赖判定、写集比对、台账校验、重跑哪些步骤的计算、进度百分比：**全是代码**。模型只做判断题（分类、起草、摘要、提取、提议）。
- 成本、耗时、token 只报工具给出的数，拿不到就说拿不到；litellm 的 `None` 与 0 都是「拿不到」。
- 进度口径（人裁 G4）：已完成 task 数／总数，在跑的给 `attempt n/max`；UI 写明「不反映难度差异」。

## 5. 明确不做（YAGNI）

1. 用 submodule 聚合各仓。
2. 自建多模型网关（用 litellm）。
3. 自建多终端插件体系（「HTTP server＋事件流＋session id」就够）。
4. 把一个 run 建模成 MCP Task（TTL 可被丢弃、取消是协作式）。
5. 用 LLM 做调度、依赖判定、写集比对、台账校验、进度估算（P7）。
6. 现在就按分布式重写控制面。
7. 在模板里写死具体 agent 和模型（机器不同；模板只写建议，人裁 2026-10-21）。
